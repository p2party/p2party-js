Date: 2026-09-07. Tree: `p2party-js` master at `b8c3f02` (HEAD, same day), `p2party-server` master at `5e76a90`. Spec: `spec/spec-architecture-l2-blind-rendezvous.md` (`S:` below). ## 0. Verdict in one paragraph

The research reports describe a tree that no longer exists. Five commits landed on 2026-09-07 after the reports were written (`5654452`, `d657ad4`, `3d3c517`, `b8c3f02`, plus the design doc `3565855`/`3c7f169`), implementing Tasks 1, 2, 3 and 7 of `docs/superpowers/plans/2026-09-07-blind-two-store-prototype.md` under `src/blindRendezvous/prototype/` (3,188 lines) with 67 passing tests, and adding 336 lines of store-wire schemas and 188 lines of signing transcripts to `schemas.ts`/`derivations.ts`. The pair SEND half — which every report called the largest gap — now exists and is tested end to end in memory (`pairDriver.ts:461-2035`, `tests/blindRendezvous/prototype/pairDriver.test.ts:251-297`). The pure store window machine (allocate / append / finalize / checkpoint chain / withhold fault / restart replay) exists (`store/storeCore.ts:269-1060`). What does **not** exist is everything that touches a network, a browser, a disk, or the two together: no HTTP handler, no server entrypoint, no SQLite, no `fetch` client adapter, no scheduler/union/backfill runtime, no `RTCPeerConnection` provider, no `createSession` composition, no E2E harness, and no flag in `connect()` (the design deliberately keeps `src/index.ts` untouched; the "flag" is the directory boundary plus a server env gate). `p2party-server` still contains zero store code (`src/` tree listed; grep for append/checkpoint/chunk is empty). Remaining work is plan Tasks 4, 5, 6, 8, 9, 10, 11: roughly 2,300–2,900 lines of source, tests and harness, all of it integration glue over primitives that are already unit-proven. The critical path is linear (store HTTP → client adapter → carrier runtime → browser composition → E2E), and no step requires inventing release bytes: the prototype's own wire prefix is `prototype-v0` (`profile.ts:63-68`), which is exactly what `S:3392-3393` permits.

## 2. Critical path to the flagged two-store demo

Target run: two headless Chromium contexts, one capability, two store processes on 5910/5911; each browser publishes PRESENCE to both stores, discovers the other via either, exchanges SDP inside pair-sealed operations, runs `createSession` over the data channel, round-trips one message; then the same run with store A killed and with store A withholding. Every step below names the spec's stub-or-fail-closed ruling with the line that decides it. LOC = source + tests, honest range, not counting docs.

Step 0 (done, `5654452`..`b8c3f02`): profile, wire codecs, store core, pair driver. Nothing to do except keep the tests green.

Step 1 — Store HTTP handler, SQLite persistence, server entrypoint (plan Task 4). ~600–750 LOC (`storeHttp.ts` ~250, `storeServer.ts` ~120, `storeSqlite.ts` ~120, tests ~250) + one `package.json` script.
- Fail-closed, may not be stubbed: every syntactically valid protocol request answers HTTP 200 with one canonical fixed-length body and one constant 400 for a malformed outer request (`S:7223-7229`); no redirects/cookies/auth/compression/ranges/room-derived headers/per-room cache keys (`S:7226-7228`); logs carry only profile/window/class/chunk/route/count/latency/outcome, never bodies (`S:1291-1296`); the process refuses to start without the two env gates (design §4.3/§6) so the prototype cannot be mistaken for a service; ports above 5000 (repo rule). Responses must be signed with the transcripts already in `derivations.ts:1595-1735` so the client can verify them.
- Stub permitted behind the flag: open allocation (token bytes ignored) — the spec's sole v1 scheme is Blind-RSA (`S:6044-6046`), and a non-conformant admission may exist only if it is not advertised as v0.4 (`S:6155-6157`, `S:3392-3393`). Idempotent replay of committed `allocated` results is already implemented (`storeCore.ts:493-616`, tested `storeCore.test.ts:286-309`) and matches `S:11939-11947`.
- Server bytes: route prefix `/p2party/prototype-v0`, descriptor path `/.well-known/p2party-store/prototype-v0`, media types `application/p2party-*-prototype-v0` (`profile.ts:63-68`). These are the prototype's own bytes, not the frozen `S:7206-7217` family; the design doc says so (§2). Do not reuse the frozen suffixes.
- Where it runs: the plan puts the entrypoint in `p2party-js` (`bun run src/blindRendezvous/prototype/store/storeServer.ts`), not in `p2party-server`, because `p2party-server` cannot import the SDK modules without a path dependency and its `index.ts:38` blocks on Postgres. That is the right call for a prototype; a later `p2party-server` store-only build is Phase 1 (`S:14101-14106`).

Step 2 — Client store adapter with chain verification and custody-breach detection (plan Task 5). ~500–650 LOC (`storeClient.ts` ~350, tests ~250 against an in-process `Bun.serve`).
- Fail-closed: descriptor validated and key pinned before any other request (`storeDescriptor.ts:329` `storeDescriptorActiveAt`); every signed response verified under the pinned key; `scanWindow` fires the checkpoint GET and every chunk GET of every class without awaiting and never narrows the class set (`S:7238-7245`); per chunk: signature over `publicChunkSigningHash(body)`, bucket equals the requested tuple, `fixedObjects.length === publicChunkObjectCount`, exact object length, `previousChunkHash` links; checkpoint: `structurallyValidCheckpoint` at the finalization instant (`ingressWindowStartMs(w) + chunkFinalizationOffsetMs`), root recomputed from all chunk hashes (`checkpointLeafEntries` + `rfc9162MerkleTreeHash`) and compared, then `verifyStoreCheckpointChain` over the observed run; a verdict other than `chain-verified`/`unverified-chain-gap` marks the store inert but its objects are still unioned (`S:6355-6358`, `S:11602`).
- Stub permitted: `PublicCustodyBreachProofV1` objects and tombstone accounting (`S:11603-11606` are accountability claims the prototype does not make) — but the plan's receipt-vs-slot compare (`S:9.12`, `S:13862-13871`) is cheap and is the only thing that turns the withhold scenario into a *detected* fault rather than a silent union; keep it.
- Not permitted: targeted `get(objectId)`, room filters, or per-room subscriptions (`S:6371-6375`).

Step 3 — Carrier runtime: fixed schedule, per-store sealing, union, backfill, witnessing (plan Task 6). ~700–850 LOC (`carrierRuntime.ts` ~450, tests ~350 with fake clock/timers and two in-process handlers).
- Fail-closed: the same operation bytes sealed once per store under `carrierContextId = publicCarrierContextId(storeId, profileHash)` (`storeDescriptor.ts:165-176`) with an independently sampled 24-byte nonce (`S:1170-1175` SEC-004, `S:6915-6924`) — never byte-identical ciphertext to two stores; publish to both stores proactively at the schedule, never to the second only after the first fails (`S:1267-1268` SEC-015); read both, `openCarrierEnvelope` per object with `null` = cover, `validateAndIdentifyOperationCandidate`, `mergeOperationCandidateSets` across stores, `coreReduce` (`S:7605`, `S:7668-7671`, `S:7797-7808`); envelope header must equal the fetched bucket and the store's context before opening (trap from `carrierEnvelope.ts:221-231`: keys derive from the header, so a store could serve another store's objects); ingress-window gate before trial decryption (`S:6944-6949`); a store that fails or omits only degrades the topology label (`S:11592`, `S:11601`) and never rolls state back (`S:1261-1262`).

## 3. Shortest honest fallback demo

The report the brief anticipated — "pair send half too large, fall back to presence-only + SDP over an ad-hoc HPKE envelope" — is moot: the pair send half exists and passes `pairDriver.test.ts:251-297` (both drivers reach `handoff`, equal `RendezvousChannelId`, crossed fingerprints, distinct `SessionRole`s, every operation delivered twice). The realistic fallbacks are smaller cuts of the remaining integration, in decreasing order of what they prove:

Fallback A — skip the browser (Steps 4–5): two Bun processes (or one process with two `PairDriver`s) over the two HTTP stores with the carrier runtime, ending at equal `HandoffFacts`; then run `createSession` over an in-memory pipe (`examples/standalone-e2ee.ts:49-66`) using the handoff's `rendezvousChannelId` and *canned* fingerprints. Proves: store-blind discovery and pair bootstrap through two independent stores with kill/withhold, union, backfill, and that the v4 session accepts the derived channel id. Does not prove: real WebRTC connectivity, real DTLS fingerprints, complete-ICE SDP sizes in a browser, or the `getStats` tripwire. Saves ~800 LOC. The privacy audit still holds because the stores' request bodies are identical to the browser run.

Fallback B — skip the scheduler (Step 3's fixed schedule and dummies): a naive runtime that appends real objects only and scans every window. Proves fault tolerance and union. Loses the per-store request-shape invariance (a store then sees when a client has something to say); this must be stated as a *known leakage class the prototype does not cover* — it is still within the field-level S1 statement (`S:11593`: timing/cohort correlation is outside the field-level guarantee) but the demo may not say the trace is fixed. Saves ~250 LOC.

Fallback C — presence-only two-store discovery (no pair flights): PRESENCE to both stores, union, `observedPresences` non-empty on both sides with A killed. Proves only the carrier layer (envelope separation, union, one-store failure). Does not prove pair privacy, SDP-in-pair, or the v4 handoff; it must not be described as rendezvous. Only worth doing as a Step-3 milestone test, not as a demo.

Recommendation: do not pick a fallback up front. Step 3 is the largest remaining unknown; if it slips, Fallback A is the honest stopping point and still exercises both fault scenarios.

## 4. What the demo may and may not say

Governing text: `S:3392-3393` ("prototype behind internal flags ... shall not independently invent release bytes and call them v0.4"), `S:3013-3020` (absent implementation is `not-implemented`; "No implementation may choose a friendlier state"), `S:1915-1920` (no runtime `L2`/`R2-BEC`/"fully secure"/"censorship-resistant" badge), `S:12234-12237`, `S:12251-12257` ("S1 never claims omission tolerance. R2-BEC is never a runtime badge"), `S:13496-13499` (qualify "first", "novel", "censorship resistant"), `S:4206-4207` ("two ordinary stores ... does not satisfy SP1 merely by name"), `S:12060-12063` (a store used by one room is `room-unique`), `S:11593` (collusion: field-level guarantee only), `docs/blind-rendezvous-implementation-status.md:282-289`, `docs/blind-rendezvous-handoff.md:510-526`.

May say (each sentence is backed by a run artefact or a test):
- "On this run, neither store's request bodies contained the room capability, the `RoomContextId`, either stable Ed25519 public key, or any SDP byte." (wire-log audit; `pairDriver.ts:743-758`)
- "Each store received a differently keyed and nonced envelope of the same operation; the two stores' objects have no common identifier." (`derivations.ts:1323-1332`; `roundTrip.test.ts:304-397`)
- "With store A killed after presence publication, the pair completed through store B." / "With store A accepting appends but finalizing dummies, the client detected the custody mismatch against its signed receipt, excluded A, and completed through B." (E2E scenarios; `storeCore.ts:723`)

## 5. Fault-tolerance scenarios and the equivocation check available today

Scenario 1 — store A down (SIGKILL after both `presence-published`). Expected per `S:11592` ("One of several stores fails: Continue fixed reconciliation with the others; do not roll state back or adapt room traffic shape") and `S:11591` (`single-carrier-dependent`). Mechanics: every fetch to A fails → runtime marks A's event missed, keeps B's schedule unchanged; B carries PRESENCE/HELLO/ACCEPT/OFFER/ANSWER; union is B-only; `storeTopology` degrades. Assert: both pages reach `message-verified`; A's request log stops; B's per-window counts unchanged. Also run the mirror (kill B) in the `all` table.

Scenario 2 — store A withholding (`P2PARTY_STORE_FAULT=withhold`: `storeCore.ts:150-151`, `:720-723` answers `stored` and never binds; finalization pads the slot with a random body at `:840`). Expected per `S:11601` (omission is availability failure; union other sources) and, because the client holds A's signed `stored` receipt, `S:9.12` / `S:13862-13871`: receipt vs finalized slot mismatch → A excluded from positive custody, room state from B unchanged. Assert: `custody-breach` fault recorded for A (plan Task 5 compare), A marked inert, both pages reach `message-verified` via B, and A's chunk at the receipt's `appendSlotCoordinates` position does not hash to the receipt's object hash. Note the honesty limit: if A simply stayed silent instead of signing `stored`, the client could report only unavailable/unknown, never blame (`S:11603`, `S:12572-12573`).

Scenario 3 (plan `unreachable-b-for-one`, optional but the strongest): page B is configured with A only; page A with both. Proves backfill: A's runtime re-wraps B's operations into A's context (`S:13789-13796`). Assert: A's chunks contain envelopes that open under the room root for operations B authored.

Equivocation checks available in the tree today (all pure, all 0 src callers, all mutation-tested in `tests/blindRendezvous/storeHonesty.test.ts` with re-signed fixtures):
- Same-window checkpoint conflict: `publicWindow.ts:636` `checkpointsConflict`, and inside `verifyStoreCheckpointChain` (`:936`) as verdict `checkpoint-conflict` with canonical order (`storeHonesty.test.ts:644-739`).
- Broken predecessor link: verdict `chain-breach` via `chainLinksSuccessor` (`:676`) / `chainValidSuccessor` (`:799`).
- Chain-start equivocation across descriptor generations: `storeDescriptor.ts:516` `chainStartConflict`, permanent (`storeHonesty.test.ts:725-737`).
- Structural checkpoint validity at the finalization instant, including descriptor rotation: `publicWindow.ts:721` (`storeHonesty.test.ts:220-456`, 12 rejection branches).
- Chunk relocation / wrong leaf / extra sibling: `publicWindow.ts:554` `verifyCheckpointChunkInclusion` (`publicWindow.test.ts:309-434`).
- Author-slot and semantic-slot forks in room state: `coreReduce.ts` faults `author-fork-or-overquota`, `presence-or-leave-fork` (arrival-independent, `S:7801-7803`).
- Pair-slot fork: `pairLedger.ts` `previewAuthenticatedPairSlotV1` → `fork` fails the edge (`pairDriver.ts:1174-1181`; `pairDriver.test.ts:379-395`).

Not available today and must be written in Step 2: chunk signature verification under the pinned key (explicitly left to the caller, `publicWindow.ts:545-553`), `finalizedChunkRoot` recomputation (`:706-712`), the composition of both with `verifyStoreCheckpointChain`, header-vs-bucket cross-check on every object, and the witness split-view compare (server half at `storeCore.ts:1029-1060`, client half absent). Chunk-level equivocation (two signed chunks for one index, `S:6355-6358`) can only be *observed* if two clients compare what they fetched — the prototype's witness exchange is the mechanism, and it is a hint, not a proof.
