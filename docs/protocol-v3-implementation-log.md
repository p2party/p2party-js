# p2party protocol-v3 — Implementation Log

> A living, stage-by-stage record of building protocol-v3 (PACE + Double Ratchet)
> on top of the offensive-cryptography transport. Source material for the paper
> and the p2party.com "road to today" blog series. Updated at each stage boundary;
> the factual backbone is `docs/design-decisions-and-security-findings.md`.

## Implementation Progress & Methodology (protocol-v3)

Protocol-v3 replaces the ad-hoc key exchange of prior versions with a balanced PAKE (CPace over Ristretto255) feeding a Double Ratchet (X25519 DH ratchet + HKDF-SHA512 symmetric ratchet), layered on top of the existing offensive-cryptography transport with its uniform 64 KiB chunk envelope. It is being built test-first and stage by stage: the plan (`docs/superpowers/plans/2026-07-22-pace-ratchet-protocol-v3.md`, committed at `9f8acc3`) decomposes the work into seven stages, each unit gated by a known-answer test (KAT) written and run *failing* before any implementation exists, and each task cleared by a two-stage adversarial review before the next begins. All work lives on `feat/pace-ratchet-protocol-v3`, branched from `master @ 9f8acc3`. This section reports Stage 1 as landed and describes the methodology that governs every stage.

### Stage 1 — cryptographic foundation

Stage 1 delivers the stateless WASM crypto primitives the ratchet is built from. Nine new C exports were added to the libsodium-backed `libcrypto.wasm` module: three CPace/Ristretto255 operations (`cpace_ristretto255_from_hash`, `cpace_ristretto255_scalarmult`, `cpace_ristretto255_scalar_random`), the X25519 DH-ratchet pair (`x25519_keypair`, `x25519_dh`), HKDF-SHA512 built on `crypto_auth_hmacsha512` (`hkdf_sha512_extract`, `hkdf_sha512_expand`), a symmetric ChaCha20-Poly1305 AEAD (`encrypt_chachapoly_symmetric`), and the AEAD message-receive path (`receive_message_with_key`). The work landed across four commits — primitive byte-size constants as the sizing single-source-of-truth (`acd7b69`), the failing KAT suite (`bcaf987`), the C wrappers plus libsodium wiring and rebuilt binary (`351a61c`), and the fixed-heap budget gate (`a848694`) — with two review-driven fix commits (`631335a`, `92b07e8`) interleaved.

The exports are correctness-anchored to authoritative vectors rather than hand-transcribed constants: Ristretto255 `from_hash` and `scalarmult(2·B)` are taken from the vendored libsodium files `test/default/core_ristretto255.exp` and `scalarmult_ristretto255.exp`; the X25519 single-iteration vector from RFC 7748 §5.2; HKDF-SHA512 from RFC 5869-style parameters and additionally recomputed at test time against `node:crypto` `hkdfSync('sha512', …)` as a live oracle; the AEAD vector from RFC 8439 §2.8.2. CPace and X25519 agreement are also computed live in both directions (K₁ = y₁·(y₂·G) = K₂ = y₂·(y₁·G), and DH(a,B) = DH(b,A)), so the suite verifies computed agreement rather than pinned magic. The one unavoidable pinned value — the AEAD KAT — is documented honestly: Bun's `node:crypto` `createCipheriv('chacha20-poly1305', …)` throws `ERR_CRYPTO_UNKNOWN_CIPHER`, so no runtime oracle exists and the RFC 8439 hex is used directly, flagged as a deliberate compromise, not a mock.

The module runs on a **fixed 2 MB heap with growth off**: `INITIAL_MEMORY=2mb` gives 32 × 64 KiB = 2,097,152 bytes, and `ALLOW_MEMORY_GROWTH=0` with `initial === maximum === 32` means the linear memory cannot grow even if the module tried. Commit `a848694` pins this as a runtime budget gate rather than a link-time claim: a fresh module is instantiated on its own 32-page `WebAssembly.Memory`, the largest single Stage-1 operation — `receive_message_with_key` over a full 64 KiB frame — is executed, and the test asserts both that it returns (a negative auth-fail on all-zero input, i.e. it did *not* OOM/abort) and that `buffer.byteLength` is still exactly 2,097,152 afterward, proving zero bytes of growth at runtime and trapping any future change to `maximum` that would silently reintroduce headroom. Adding the Ristretto255/X25519/HKDF/AEAD libsodium sources grew the binary from 136,797 to 158,379 bytes (≈155 KB, a ~22 KB increase under `-O3 -flto --gc-sections`), leaving wide margin under the 2 MB heap; dead-code elimination stripped the unused `core_ed25519` hash-to-curve path so the planned contingency to drop `core_h2c.c` was never needed. The wrappers allocate only stack buffers, and libsodium's `randombytes.c` is deliberately *not* compiled — all entropy is generated in JS and passed in as seeds, with a tiny `getentropy`-backed provider covering the only two exports that need it. A design consequence carried forward: because the WASM heap is fixed but the JS heap can grow, the Double Ratchet's out-of-order skipped-message-key map lives in JS (`state.skipped`, bounded by `MAX_SKIP=512` as an anti-DoS cap), and the WASM exports remain stateless one-shot primitives.

Stage 1 closed green: the KAT suite moved from 0 pass / 8 fail (RED) to 8 pass / 0 fail / 23 `expect()` calls against the rebuilt WASM, the full `pake_ratchet.test.ts` file stands at 9 pass / 0 fail / 25 `expect()` at branch HEAD, and the whole repository regresses clean (`bun test`: 34 pass / 0 fail across 10 files; `npm run typecheck` clean on the production tsconfig). Export existence was proven three independent ways after the production build (`grep` of each symbol in the emitted `libcrypto.js`, a runtime `typeof mod._<name> === 'function'` check for all nine, and the KAT bodies actually reaching each export's assertions), and the SSOT export wiring was verified in all three required locations (`scripts/emscripten.js`, `scripts/libcrypto.d.ts`, and the build-regenerated `src/cryptography/libcrypto.d.ts`).

### Methodology

Every unit follows a strict TDD red-green discipline with the KAT as the gate and 0-fail as the sole pass condition. The failing state is proven *genuine* rather than accidental: for the KAT suite, `beforeAll` loaded the module cleanly from a local `wasmBinary`, so the harness demonstrably reached every test body, and each of the eight failures was a `TypeError: mod._<name> is not a function` naming one specific missing export — cross-checked against the actual pre-Task-3 `libcrypto.js` export list, which contained only the pre-existing `_argon2/_malloc/_free/_sign/_verify/…` symbols and none of the nine new ones. This confirms the RED reason was "not built yet," never a mistranscribed vector or a broken test. Reviewers additionally re-verified the vectors byte-for-byte, diffing the committed test file programmatically against the brief's source fences (the only deltas were a cosmetic formatter line-collapse and a trailing newline) so that every hex constant matched its libsodium/RFC origin verbatim before the suite was accepted.

Each task was gated by a two-stage adversarial subagent review — a spec-compliance pass followed by a code-quality pass — recorded in the progress ledger as "review Approved," with follow-up fixes required to land before the next task proceeded. This produced real, non-cosmetic catches. The code-quality pass caught a `tsc` typing defect where the test passed a `Buffer` (from `readFileSync`) into an emscripten factory typed for `wasmBinary: ArrayBuffer`, fixed by copying into a fresh `ArrayBuffer` (`631335a`) and then promoting that fix into the shared test-module loader so every later task inherits it. It also flagged two exports (`_cpace_ristretto255_scalar_random`, `_hkdf_sha512_expand`) that had been *shadowed* behind earlier `throw`s in their RED bodies, and required Task 3 to independently re-confirm each reaches and passes its own assertions once the earlier calls succeeded.

The headline result of the review, though, was catching a **real design bug in the plan before anything round-tripped**. The plan specified the per-chunk AEAD nonce as `nonce = chunkIndex`. Review recognized this as *physically unrealizable at decrypt time*: `chunkIndex` lives inside the encrypted per-chunk metadata, so the receiver cannot know the nonce until after it has decrypted — yet it needs the nonce *in order to* decrypt. The two obvious repairs are both broken: reusing one message-level value (the 8-byte `N` counter) across every chunk under a single key is catastrophic ChaCha20-Poly1305 nonce reuse, and carrying a raw chunk index in cleartext leaks chunk count and ordering to an on-path observer. The user-approved correction (`92b07e8`) makes the per-chunk nonce a fresh **random 12-byte value carried in the cleartext frame header** — receiver-derivable because it is literally on the wire, metadata-safe because it is random rather than an index, and birthday-safe within a single per-message key — and re-cut the frame layout accordingly (`RATCHET_NONCE_LEN=12`; `CHUNK_HEADER_LEN` 49→61; `MESSAGE_START` 50→62), with the standing rule that a retransmit MUST resend the *identical* cached `(nonce, ciphertext)` pair. Because the receive path was still only smoke-tested when this was found (a garbage frame returns `< 0`) and no send↔receive round-trip yet existed to expose it empirically, the bug would otherwise have survived undetected into a stage where it is far more expensive to unwind — a concrete illustration of the value of adversarial review over self-review. The design doc and global constraints were corrected in the same commit; the C-level frame `#define`s and the placeholder nonce in `receive_message_with_key` are intentionally left at their old values with an in-code note, scheduled for reconciliation in Stage 5 alongside the first real send↔receive round-trip KAT.

### Remaining stages

Stages 2–7 build outward from this foundation — the JS-side ratchet state machine, session and framing integration, the Stage-5 send↔receive round-trip and frame-layout reconciliation, and end-to-end verification — each held to the same KAT-first, review-gated discipline; Stage 2 is already in progress on the branch (`f6debae`). The uniform-chunk transport also pre-provisions a future post-quantum KEM at no wire cost (a reserved `PQ_EPOCH` byte and `PQ_TAG` channel input), since a hybrid ML-KEM/X-Wing ciphertext fits whole inside a single 64 KiB chunk without a v4 wire break.

### Stage 2 — pure-crypto units + the review as a safety net

With the WASM primitive layer pinned and reproducible, Stage 2 lifts five self-contained TypeScript units onto it. Each is a thin, allocation-disciplined wrapper around the Stage-1 exports rather than a fresh implementation of the math — the arithmetic stays in audited C, and the TS layer owns only marshalling, buffer hygiene, and the higher-level protocol logic. Every unit was written test-first, and — this is the load-bearing methodological choice — every unit is gated on a *live* correctness oracle: a two-party agreement that must actually converge, or a known-answer test checked against an independent implementation, never a magic constant pinned from our own first run. A vector we generate and then assert against tells us only that the code is self-consistent; a vector produced by `node:crypto` or by the counterpart role tells us the code is *correct*.

**x25519 (`src/cryptography/x25519.ts`, `f6debae`, `26d353f`).** Wraps the Stage-1 `_x25519_keypair` / `_dh` exports in the house malloc / copy-out / zeroFree pattern, and establishes the shared test harness the rest of the stage reuses: a `testModule.ts` loader that reads and instantiates the fixed 2 MB `libcrypto.wasm` for the Bun unit runner, aliasing `globalThis.window` at import time with no per-call memoization, plus the primitive interface size constants. The DH secret and the keypair failure path were the subject of a review catch (below), fixed in `26d353f`.

**hkdf (`src/cryptography/hkdf.ts`, `fc4eb8d`).** Exposes `hkdfExtract` / `hkdfExpand` over the RFC 5869 HMAC-SHA512 exports, following the same secret-material discipline: the PRK (both the extract output and the copy re-malloc'd inside expand) and the derived OKM are `zeroFree`'d, while the salt / IKM / info scratch buffers are plain-`_free`'d. The tests assert determinism, `outLen`- and `info`-label separation, the brief's verbatim `T(1)`-prefix KAT, and — the live oracle — two assertions against `node:crypto.hkdfSync('sha512', …)` covering both single- and multi-block expand. Reviewed and approved with no issues.

**cpace (`src/cryptography/cpace.ts`, `b3b69b7`, `e5f6348`, `58c02a4`).** A CPace PAKE on Ristretto255: `deriveGenerator` computes `G = ristretto255_from_hash(SHA512(CPACE_DOMAIN ‖ PRS ‖ sid ‖ CI))`, `cpaceStart` samples a scalar `y` and returns `Y = y·G`, and `cpaceShared` returns `K = y·Y_peer`, surfacing the scalarmult identity/error return (`-1`) as a thrown exception rather than a silent zero `K`. The scalar `y` and the shared `K` are `zeroFree`'d; public and scratch buffers are plain-freed. Tests cover two-party agreement and wrong-PIN divergence. The transcript construction was hardened during review (`e5f6348`), with a spec correction in `58c02a4`.

**x3dh (`src/cryptography/x3dh.ts`, `9606d43`, `b4b713d`).** Computes the identity-mixed X3DH shared secret (no PIN), with the DH ordering verified both algebraically and in code for the initiator and responder roles. Review added the missing symmetric negative control (`b4b713d`). One minor item is carried forward to final review: the plain-JS DH intermediates have no wipe-on-throw `try/finally`.

**ratchet (`src/cryptography/ratchet.ts`, `749e3d2`, `8bba4e9`, `d65ce73`).** A Signal-style Double Ratchet expressed as a per-logical-message key schedule; there is deliberately no AEAD at this layer — that wiring lands in Stage 5. `kdf_rk` is HKDF extract+expand over `(root, DH)` yielding 64 bytes split 32/32; `kdf_ck` is two domain-separated HMAC-SHA512s over the chain key. A DH step fires whenever a header's `dhPub` differs from the stored `dhRemotePub`. Out-of-order delivery is absorbed by a bounded skipped-key map keyed by `(dhPub, N)`, with a per-decrypt `MAX_SKIP = 512` throw as an anti-DoS bound. The initiator opens its sending chain at init from the responder's public key; the responder opens both chains on first inbound message. Retired roots, chain keys, and DH secrets are wiped, and `serialize` / `deserialize` round-trips the full state including the skipped map. Review (`8bba4e9`, `d65ce73`) added a global skipped-key cap, header integer validation, and an honest decrypt doc-comment (below).

#### Stage-1 revision: swapping in libsodium's native HKDF (`d8ae95b`)

After the units were complete, a user decision on 2026-07-22 replaced the hand-rolled RFC 5869 HKDF (built on `crypto_auth_hmacsha512`) inside the WASM with libsodium's own `crypto_kdf_hkdf_sha512_extract` / `_expand`. Concretely: `crypto_kdf/hkdf/kdf_hkdf_sha512.c` and its dependencies were added to `scripts/paths.js`, and only the *bodies* of the `_hkdf_sha512_extract` / `_expand` wrappers in `pake_ratchet.c` were swapped to call the native routines. Export names and signatures were kept identical, so `hkdf.ts` and every downstream consumer (cpace, x3dh, ratchet) were untouched. The change was queued to apply serially, immediately after the in-flight ratchet fix committed, to avoid a concurrent-commit git race.

The justification is the same live-oracle standard the units are held to: the `pake_ratchet` HKDF KAT stayed **byte-identical** against `node:crypto.hkdfSync`, the full 51/51 suite (hkdf, cpace, x3dh, ratchet) and typecheck stayed green, and `npm run predist` rebuilt the WASM and re-pinned its SRI hash. Replacing a hand-rolled construction with a standard-library one is exactly the kind of change that can silently shift output; the independent oracle is what lets us assert it did not.

#### Methodology: adversarial review as a safety net

The strongest evidence for the two-stage (spec + quality) review is not that it polished style — it is that across Stages 1 and 2 it caught **five genuine issues before any of them shipped**, several of which a green test suite alone would never have surfaced. A test suite confirms the properties you thought to assert; it is silent on the properties you forgot, and on designs that cannot round-trip in the first place.

1. **Unrealizable "nonce = chunkIndex" AEAD design** (Stage 1, Task 3; *critical / design-blocking*). The planned per-chunk nonce could not exist: `chunkIndex` lives *inside* the encrypted metadata, so the receiver cannot know it pre-decrypt; a message-level value reused across a message's chunks would break ChaCha20-Poly1305; and a cleartext raw index would leak chunk count and order. Caught before anything round-tripped. The user-approved redesign carries a fresh random 12-byte nonce in the cleartext frame header per chunk — metadata-safe, birthday-safe within a per-message key, and deterministic on retransmit via the cached `(nonce, ciphertext)` pair — with `RATCHET_NONCE_LEN = 12`, `MESSAGE_START` 50→62, `CHUNK_HEADER_LEN`→61, and the spec/plan constraints corrected (`92b07e8`).

2. **CPace transcript ambiguity** (*important*). `SHA512(DOMAIN ‖ PRS ‖ sid ‖ CI)` by bare concatenation becomes ambiguous once Stage-4 CI binds variable-length data: distinct `(PRS, CI)` pairs can collide to the same generator `G`, amplifying online PIN guessing. The fix mandates IRTF-CPace `lv_cat` length-prefixing of each transcript field, and the same change wiped the `PRS` (PIN) bytes left in the WASM heap (`b3b69b7`, `e5f6348`, `58c02a4`).

3. **Unwiped X25519 DH secret** (*critical*). The DH shared secret and the keypair failure path were freed without `zeroFree`, leaving secret key material in the WASM heap on free. Fixed to zero before free, matching the wrapper's secret-material convention (`26d353f`). A passing agreement test proves the secret is *correct*; it says nothing about whether it was *erased*.

4. **X3DH test blind to half its mutual-auth property** (*test-coverage / important*). The tests bound the peer's identity but had no symmetric control for the initiator's own identity `IK_a` — had `IK_a` been dropped from the DH mix, every test would still have passed. The added negative test corrupts `IK_a` and asserts two-party agreement breaks, restoring the symmetric initiator-identity binding control (`b4b713d`).

5. **Ratchet replay-desync + unbounded skipped keys** (*two important + one minor*). Two hazards surfaced: (#1) `ratchetDecrypt` mutates state *before* AEAD authentication, so a duplicate or replayed old-chain message — reachable via our own retransmit layer — fires a spurious backward DH step and desyncs the session; and (#2) only the per-decrypt `MAX_SKIP = 512` bound existed, with no global cap on total retained skipped keys, making RAM and persisted-row growth unbounded (and the plan's "capped at MAX_SKIP" comment simply false). #2 was fixed now: `MAX_SKIP_SESSION = 2000` with evict-oldest, header integer validation (`Number.isInteger`, `>= 0`), an honest `ratchetDecrypt` doc-comment, and the false comment corrected (`8bba4e9`, `d65ce73`). #1 is deferred to Stage 4/5 as a documented caller contract in the plan's Global Constraints: run `ratchetDecrypt` on a serialize/deserialize *clone*, commit state only after AEAD authenticates, and dedup already-seen `(dhPub, N)`.

Three of these five — the unwiped DH secret, the `IK_a` blind spot, and the ratchet replay-desync — are latent *security* bugs, not stylistic notes, and each would have passed the unit suite as written. That is the argument for treating adversarial review as a required safety net rather than a courtesy pass: the failures that matter most are precisely the ones the existing tests are, by construction, unable to see.

### Stage 3 — session persistence + at-rest encryption

A Double Ratchet earns its forward secrecy and post-compromise security by *deleting* key material: every ratchet step wipes the root, chain, and DH secrets it just superseded (Stage 2, `749e3d2`), so a later compromise cannot walk backward or forward past the messages it directly touched. But that guarantee is only as durable as the *live* state that produces it, and in a browser the live state is the most perishable thing there is. A ratchet that exists only in a tab's heap dies with the tab: a page refresh — the single most ordinary event in a browser session — throws away the whole ratchet and forces the two peers back to a fresh handshake, collapsing the ratchet's continuity and dropping the pair back toward the naive per-chunk scheme protocol-v3 exists to retire. The obvious repair, writing the ratchet to disk so it survives the refresh, is itself a trap if done naively: IndexedDB is plaintext at rest, so a session persisted in the clear hands a full DB dump every root and chain key the ratchet was so careful to rotate. Forward secrecy is about deleting the *old* keys; persistence is about protecting the *current* ones, and Stage 3 is the half of the ratchet that does the latter. It is also, concretely, the "IndexedDB + WebCrypto" line of the grant promise — the native-browser realization of Signal's ratchet, where the browser's own structured storage and its own key-handle-based crypto stand in for the mobile keystore that Signal leans on.

**The row shape (`src/db/types.ts`, `5bedc9b`).** Task 1 is type-level only and lands the persisted record before any code touches it. The `RatchetSession` interface is the full ratchet state made durable: the secret core (`rootKey`, `sendingChainKey`/`receivingChainKey` — both nullable, `dhSelfSec`) plus the public and bookkeeping fields (`dhSelfPub`, `dhRemotePub`, the `Ns`/`Nr`/`PN` counters, `peerId`, `updatedAt`) and the out-of-order `skippedMessageKeys` array, each entry a `{ dhPub, n, messageKey }`. Two decisions are baked into the type and carried in its doc-comment. First, a session is keyed by the **stable identity edge** `(roomId, peerPublicKey)`, not by the ephemeral per-connection `peerId` — which changes on reconnect — precisely so the ratchet survives reconnect and reload rather than forking a new session each time the socket flaps. Second, only the secret fields are meant to be stored wrapped; the public and counter fields stay cleartext. The same commit adds the three worker message variants (`getRatchetSession`, `setRatchetSession`, `deleteRatchetSession`) to the `WorkerMessages` union and their return types, and pins `fake-indexeddb` at exactly `6.2.5` as a devDependency (no caret, unlike its siblings) so the whole IndexedDB + WebCrypto layer can be exercised under `bun test` without a real browser. The `skippedMessageKeys` cap (`MAX_SKIP_SESSION`, evict-oldest) is a Stage-2 ratchet-layer constraint carried into the type, not enforced here. No new tests were added — 51/51 existing bun tests still pass.

**The additive migration (`src/db/src/getDB.ts`, `7ec1776`).** Task 2 bumps `dbVersion` from `16` to `17` and adds exactly two object stores. `ratchetSessions` uses the composite keyPath `["roomId", "peerPublicKey"]` matching the identity edge, with three non-unique indexes — `peerId`, `peerPublicKey`, `roomId` — so callers can enumerate sessions without deserializing every row. `meta` is an out-of-line store keyed by a plain string whose value is a `CryptoKey`; its comment reserves it for the single non-extractable wrap key that Task 3 will install, storing the live key object (structured-cloneable) and never its raw bytes. Both stores are created only inside `if (!db.objectStoreNames.contains(...))`, i.e. purely additively — unlike the seven legacy stores, they carry no `else` branch that back-fills indexes on an existing store, because they cannot exist before v17. The migration was proven, not assumed: the test suite ran RED against the pre-edit v16 schema (4/4 fail) and GREEN after the schema change (4/4 pass), and the additive test opens a *populated* v16 database, upgrades it to v17, and verifies the existing `chunks` data survives byte-for-byte — the guarantee that shipping this migration does not disturb anyone's already-stored files. Full suite: 55/55.

**The at-rest wrap (`src/db/ratchetWrap.ts`, `fe4f159`).** Task 3 is the security-load-bearing one, and it is where the WebCrypto half of the promise is cashed out. `getWrapKey()` generates a 256-bit AES-GCM key with `crypto.subtle.generateKey({ name: "AES-GCM", length: 256 }, false, ["encrypt", "decrypt"])` — the literal `false` in the second argument makes the key **non-extractable** — and persists it in the `meta` store under the constant `WRAP_KEY_META_ID = "ratchetWrapKey"`. `wrapSecret(key, bytes)` draws a fresh random 12-byte IV per call (`crypto.getRandomValues(new Uint8Array(12))`), encrypts under `"AES-GCM"`, and returns the blob `iv ‖ ciphertext+tag` — IV in bytes `[0,12)`, ciphertext-and-GCM-tag in `[12, end)`; `unwrapSecret` slices the same way (`subarray(0,12)` as IV, `subarray(12)` as ciphertext). `wrapRatchetSession` / `unwrapRatchetSession` transform *only* the secret fields — `rootKey` always, `sendingChainKey` and `receivingChainKey` only when non-null (a `null` chain stays `null`), `dhSelfSec` always, and each `skippedMessageKeys[].messageKey` — spreading everything else (`...s`) through untouched, so `roomId`, `peerPublicKey`, `peerId`, `dhSelfPub`, `dhRemotePub`, the counters, `updatedAt`, and each skipped entry's `dhPub`/`n` remain cleartext.

Three of those choices are deliberate and each buys something specific. The **fresh random IV per wrap** is not incidental hygiene: the ratchet re-persists its session on *every* step, so the same wrap key encrypts a great many blobs over a session's life, and a fixed GCM IV reused across two encryptions under one key is catastrophic — it is exactly the nonce-reuse failure AES-GCM does not survive. **Only the secret fields are wrapped**, and the rest left cleartext, so the three `ratchetSessions` indexes still resolve against real values: `roomId`, `peerPublicKey`, and `peerId` are queryable and the counters are readable without a decrypt, which would be impossible if the whole row were a single opaque ciphertext. And the **composite keyPath** means a peer's identity-key rotation lands as a *new* row — a different `(roomId, peerPublicKey)` tuple — rather than clobbering the prior session, so a rotation never silently overwrites still-live state.

The honest scope of "non-extractable" is written into the code comment and worth stating plainly here. Because the key is generated `extractable: false` and only ever lives as a `CryptoKey` handle in the `meta` store, a full IndexedDB dump yields wrapped ciphertext plus an opaque handle whose raw bytes WebCrypto refuses to export — a Task-3 test confirms `exportKey('raw', …)` rejects. That defeats raw-key exfiltration and cross-device copy: the key material never leaves this browser as copyable bytes. It does **not** — and the comment says so — defeat an attacker who already holds the device *and* the origin. An in-page script running under the same origin (say, via XSS) can still *use* the handle to `decrypt`, because non-extractable bars export of the bytes, not use of the key. The property bought is "the keys never leave this browser as copyable material," not "the keys cannot be used by code running as this origin." One further fact mattered enough to pin down rather than assume: whether `fake-indexeddb` `6.2.5` can round-trip a non-extractable `CryptoKey` at all, since the whole reload story rests on it. The committed reload test (`ratchetWrap.test.ts`) stores the wrap key, re-reads it through a simulated reload, and then successfully *decrypts* a previously wrapped secret with the round-tripped handle (via `unwrapSecret`) — so `getWrapKey()`'s real persistence path is exercised, not a stub, and the persisted non-extractable key is shown to remain usable after reload. (The commit message corroborates that the structured clone preserves the key's non-extractable character; the finer-grained structured-clone assertions live in the task report rather than the committed test.) The commit message states no numeric pass/fail count, deferring to the task report.

**The worker and the API surface (`src/db/db.worker.ts` `1da2c27`; `src/db/api.ts` `4da1719`).** Task 4 wires three functions into the worker. `fnGetRatchetSession` reads the raw row by its `[roomId, peerPublicKey]` key, returns `undefined` if absent, else fetches the wrap key and `unwrapRatchetSession`s before handing it back. `fnSetRatchetSession` inverts that — `getWrapKey()`, `wrapRatchetSession`, then `db.put` — and stamps `updatedAt: Date.now()` *after* wrapping, the one field unconditionally rewritten worker-side regardless of what the caller passed. `fnDeleteRatchetSession` is a straight keyed delete. All three sit in `try/catch` that logs and, for get, returns `undefined` — matching the existing worker convention. The corresponding `onmessage` cases dispatch through the same shared envelope every other method uses. Task 5 is deliberately thin: three one-line `api.ts` wrappers (`getRatchetSession`, `setRatchetSession`, `deleteRatchetSession`) that pass straight through to the generic `callWorker` bridge with no extra logic, typecheck-gated to match the message union. It landed controller-verified as three thin wrappers, no scope creep, 66/66.

This is also where the offensive-cryptography thread stays intact across the persistence boundary. The `ratchetSessions` store is scoped one row per identity edge, and — this is the point — the row is a session-state record, not a traffic log. No message plaintext, no chunk, and no on-the-wire ciphertext is ever written here; the wrapped fields hold the secret key material and the cleartext fields hold only non-secret ratchet bookkeeping — the identity edge, the message counters, and the DH *public* keys (`dhSelfPub`, `dhRemotePub`, and each skipped entry's `dhPub`). The at-rest layer does not become the thing that leaks what the flooded, noise-padded wire was built to hide.

#### Methodology / decisions: the safety-net review, and a race found already closed

Stages 1 and 2 made the case for adversarial review by counting bugs it caught before they shipped. Stage 3's review is a different and, in its way, stronger data point: the review's most load-bearing act was to confirm that the one plausible concurrency hazard was **already structurally closed**, and then to catch that the code's *own comment understated its own safety*. A green suite can tell you a wrap round-trips; it cannot tell you whether two browser tabs racing to create the wrap key on first run will diverge, and it cannot tell you whether the prose describing that race is too pessimistic. The review had to reason about IndexedDB's transaction semantics to answer either.

Task 3 was approved with five security properties explicitly verified: fresh IV per wrap; non-extractable key; 1:1 secret-field coverage (a dedicated test asserts every public/counter field is byte-unchanged through a wrap while every secret field differs pre-unwrap and matches post-unwrap); get-or-create persistence across a simulated reload; and decrypt-failure surfaced rather than swallowed (unwrapping with the wrong key simply throws, which is the intended behavior). The concurrency finding is the interesting one. `getWrapKey()` uses double-checked locking: a cheap read outside any transaction as the fast path; on a miss, a *speculative* `generateKey` performed outside any transaction (so key generation never holds an IDB transaction open); then an authoritative re-check inside a `readwrite` transaction on `meta`, immediately before the `put` — and if that inner read finds a key another caller committed first, the freshly generated key is discarded and the already-stored one returned, so a single writer's `put` wins and every loser converges on it. The Task-3 report itself described the residual cross-tab first-run case cautiously, as an "accepted limit" that "just triggers a re-handshake." The review upgraded that framing: because IndexedDB serializes `readwrite` transactions across connections, the double-check inside the `readwrite` transaction is a real mutex, not merely documentation — the race is closed, and what remains is at worst a liveness note (a rare re-handshake), never a security hole. It recorded the report's more pessimistic wording as an over-statement of risk needing doc polish, not a code fix.

Two minor items were carried to final review, both non-blocking. Task 3: `getWrapKey` lacks a `try/finally` around the `meta` transaction, so an error on that path leaks the connection — a one-line fix. Task 4: the new worker functions do not `db.close()` on the throw-before-close path — explicitly noted as matching the pre-existing file convention (`fnSetDBChunk`, `fnSetDBNewChunk`, `fnSetDBSendQueue` share the exact shape), a file-wide follow-up rather than a Stage-3 regression. And one deferral is logged honestly: the real-browser structured-clone of a non-extractable `CryptoKey` is confirmed so far only against `fake-indexeddb`, and is flagged for confirmation in the Stage-7 end-to-end pass on a real browser — the residual caveat behind the otherwise-genuine reload test. (For the chronological record: the Stage-1 HKDF swap to libsodium's native `crypto_kdf_hkdf_sha512` — `d8ae95b`, logged above — landed immediately *before* this Stage-3 sequence began, not within it; the commit that actually falls between two Stage-3 tasks is the Stage-2 documentation commit `2fca609`, sequenced between Task 1 and Task 2. Neither touches the persistence work.)

Stage 3 closed complete across all five tasks (`5bedc9b`, `7ec1776`, `fe4f159`, `1da2c27`, `4da1719`), each review-approved: the `RatchetSession` type and worker variants, the `16 → 17` additive migration with its two new stores, the non-extractable WebCrypto AES-GCM wrap with fresh IV and only-secret-fields coverage persisting across reload, the `db.worker` functions with the raw-row-is-ciphertext test that has teeth, and the `api.ts` wrappers. This is the "IndexedDB + WebCrypto" deliverable of the grant, and with it the ratchet now survives the refresh that would otherwise have quietly demoted the whole mesh back to the naive scheme.

### Stage 4 — handshake orchestration

Stages 1–3 assembled a workbench of parts that could not yet talk to each other: stateless WASM primitives (Stage 1), the allocation-disciplined TS units that wrap them (Stage 2), and the encrypted-at-rest store that outlives a refresh (Stage 3). Stage 4 is where those parts become a *protocol* — the point at which two browsers, over the live DTLS data channel, actually run a handshake to end and agree on the single 32-byte root secret that seeds each edge's Double Ratchet. Nothing here invents new math; the stage is orchestration, sequencing, and — as it turned out — four review catches, two of them latent security bugs, that never reached the wire.

**The 1-byte frame-type classifier (`src/handlers/frameType.ts`, `src/utils/constants.ts`, `e0d849b`).** The pre-v3 inbound router classified data-channel frames by *length alone* — a 64-byte frame was a receipt, a `MESSAGE_LEN` frame a chunk — which cannot survive a protocol that now carries handshake HELLO/CONFIRM frames of their own sizes on the same channel. Task 1 replaces the length test with an explicit 1-byte type tag at the head of every frame: `FRAME_TYPE_HANDSHAKE = 1`, `FRAME_TYPE_CHUNK = 2`, `FRAME_TYPE_RECEIPT = 3`, plus `FRAME_TYPE_LEN`, `PROTOCOL_VERSION = 3`, and the `PQ_TAG` transcript marker. The constants are a byte-matched single source of truth across the language boundary: the same five values are `#define`d in `src/cryptography/utils.h`, and `src/utils/constants.test.ts` mechanically parses the C header with a `#define\s+NAME\s+(\d+)` regex and asserts each TS export equals its C counterpart — so a future edit that drifts one side fails a test rather than silently mis-routing frames. `classifyFrame` itself is a pure, total function: every `Uint8Array` (including the empty one, reported as `type: -1` for log-and-drop) maps to a defined `{type, payload}`, with `payload` a zero-copy `subarray` view over the same buffer. It landed deliberately *unwired* — the real inbound router still runs the old length-only path until Stage 4 Task 5 rewires it — with the full suite green at 72/72.

**The per-peer `ratchetEstablished` promise gate (`src/handlers/ratchetGate.ts`, `b21fe78`, fix `4b98c62`).** A handshake is asynchronous but message sends are not willing to wait politely, so Stage 4 needs a synchronization primitive that lets any number of would-be senders block until a given peer's ratchet exists. Task 2 adds a per-peer gate: a `Map<peerId, Gate>` of lazily-minted promises, where `getRatchetGate(peerId)` returns the same promise until `resetRatchetGate` clears it, `openRatchetGate` resolves it once the ratchet is live, and `rejectRatchetGate` fails it once (guarded by a `settled` flag so a second settle is a no-op), with three new optional `IRTCPeerConnection` fields (`ratchetState`, `session`, `ratchetEstablished`) holding the live handle off the Redux store. The review caught two things a green suite would not. The smaller: the brief's own memoization test was a tautology — `expect(getRatchetGate("B")).not.toBe(getRatchetGate("B") && null)` triggers TS2801 (a `Promise<void>` is provably never falsy) and at runtime collapses to `not.toBe(null)`, testing nothing — replaced with an assertion that actually verifies both halves of its title (same promise while unreset, a fresh one after reset). The larger was an **unhandled-rejection hazard**: `rejectRatchetGate` fired for a peer nobody had yet awaited rejects a brand-new promise with zero listeners attached, so the runtime's unhandled-rejection event fires even though a consumer that `await`s a tick later still receives the error correctly. The existing 5/5 tests missed it because every one attached its handler in the same synchronous tick. The fix is a synchronous no-op `promise.catch(() => {})` at construction inside `ensure()` — which suppresses the spurious event without consuming the rejection for real awaiters (a promise may have many listeners) — proven by a regression test that crosses two real macrotask boundaries before asserting the unhandled-rejection listener never fired, then attaches a late consumer and confirms the error is still observable (6/6, `4b98c62` re-reviewed APPROVED).

**The DTLS-fingerprint MITM binding (`src/handlers/handleHandshake.ts`, `445aaea`, fix `2af322b`).** Task 3 lands three binding helpers. `buildChannelInput` constructs the CPace channel input `CI = channelId ‖ IK_a ‖ IK_b ‖ fp_a ‖ fp_b ‖ PQ_TAG` (initiator/responder identity keys and the two DTLS certificate fingerprints, `a`=initiator, `b`=responder), so the handshake transcript is cryptographically bound to *this* DTLS session's certificates; `parseFingerprintFromSdp` decodes the `a=fingerprint:sha-256` line to 32 raw bytes; and `verifyDtlsFingerprints` cross-checks the SDP-advertised fingerprints against the *live* certificates read from `epc.getStats()`, throwing on any disagreement — the tripwire that a signaling-layer man-in-the-middle, who must present its own DTLS cert, would trip. The review found this tripwire **failed open**. The original guard read `if (liveRemoteFp !== null && liveRemoteFp !== remoteSdpFp) throw` — but `certificateFingerprint` legitimately returns `null` when the transport stat is missing, `remoteCertificateId` is absent, or no matching certificate stat exists, and that `null` short-circuits the `&&`, so a tripwire that *could not read the certificate at all* resolved successfully and waved the session through. The narrative here is the canonical one: the check meant to catch a MITM would silently pass precisely when it was blindest. The fix rewrites both terminal guards to fail closed — `if (liveRemoteFp === null || liveRemoteFp !== remoteSdpFp) throw`, and symmetrically for the local branch — so "cannot verify" is treated identically to "mismatch," proven by a regression test whose mock `getStats()` omits the remote certificate entirely and asserts a throw (7/7; full suite 84/0; `2af322b` re-reviewed APPROVED). Two documented deviations from the brief's sample code were both forced by real types rather than preference: a synchronous hand-rolled byte-concat instead of the codebase's `async concatUint8Arrays` (the interface and test require a synchronous return), and certificate-stat matching via the `forEach` callback's own `key` argument instead of a `stats.get(id)` fallback (the project's `RTCStatsReport` DOM typing exposes only `forEach`).

**The handshake core (`performHandshakeCore` + `runHandshake`, `c835244`).** Task 4 is the orchestrator proper. `performHandshakeCore` runs the two-round exchange over a transport-agnostic `HandshakeTransport { send, recv }`: round 1 both peers send a `HELLO` carrying a random `sid`, an ephemeral X25519 `EK`, and (PIN mode) a CPace `Y`, then each derives the 32-byte root secret — no-PIN via `x3dhDeriveSecret`, PIN via `G = deriveGenerator(pin, …, CI)` and `K = cpaceShared(y, Y_peer)`; round 2 exchanges the DH-ratchet public key and a *bidirectional* key confirmation, `mac_R = HMAC-SHA512(secret, T ‖ 0x02)` and `mac_I = HMAC-SHA512(secret, T ‖ 0x01)` over a byte-identical ordered transcript `T`, the distinct role bytes domain-separating the two MACs so neither can be reflected as the other. The security property is that a swapped certificate or a wrong PIN changes the derived `secret` (the HMAC key) while leaving `T` identical, so *both* legs' verify fails — asserted by a wrong-PIN test that requires `results.every(rejected)`. Crucially, `performHandshakeCore` never persists and never touches the gate; the atomic boundary lives in `runHandshake`, which sequences DTLS-fingerprint verify → core → (only on resolve) wrap + `setRatchetSession` → set `epc.ratchetState`/`session` → `openRatchetGate`, with a single `catch` that routes *every* failure to `rejectRatchetGate` + rethrow having persisted nothing. The gate therefore opens only after the session is durably on disk, and a failed handshake yields no usable state — fail-closed, exactly like the DTLS check.

The review adjudicated three deviations the implementer flagged, each a case of the code being made honest rather than convenient. First, the **empty-`sid` generator**: because round 1 is a single simultaneous HELLO, neither party knows the peer's `sid` before it must publish `Y`, so the brief's canonical-`sid` recompute simply never agrees; both legs instead derive `G = deriveGenerator(pin, sid=∅, CI)` identically, with freshness carried by CI and the random `sid`s folded into the key-confirmation transcript — a deliberate, commented deviation, flagged as a Concern for the design owner rather than smuggled in (it is exactly what D1 later revisits). Second, the **send-MAC-before-verify ordering**: the brief had the initiator verify `mac_R` before sending `mac_I`, which on a wrong PIN aborts the initiator before it ever sends, hanging the responder's `recv()` forever; the fix sends `mac_I` (which needs only the transcript `T`, not the ratchet) *before* verifying `mac_R`, so both legs reject independently, while `initRatchet` still runs only after `mac_R` verifies. The review confirmed this leaks no offline-dictionary oracle — CPace already caps a MITM at a single online guess per session, and `mac_I` reveals nothing an offline attacker can test without breaking CPace itself. Third, and most usefully, the no-PIN path **failed loud**: as wired, `idSelfSec = hexToUint8Array(secretKey)` reads the 64-byte Ed25519 store secret and feeds it into `x25519Dh`, which expects a 32-byte X25519 scalar — a `.set()` RangeError at runtime rather than a silently wrong shared secret. Flagged as Concern #1, it became the seed of the entire D2=B work below. Task 4 closed at 10/10 handshake tests, full suite 88/0, review APPROVED with no Critical/Important.

#### The two hard calls — D1 and D2 (summary; full treatment in the decision log)

Two genuinely-open questions surfaced by the Stage-4 core were escalated to the design owner and decided on 2026-07-22, grounded in a standards/SOTA rigor analysis (the companion memo, workflow `wf_a20541e8-a93`) and recorded in full — tension, option table, standards citations — as **D1** and **D2** in `docs/protocol-evolution-decision-log.md` (§2, commit `cbf57c8`). In brief: **D1** resolves the empty-`sid` Concern in favour of an **initiator-random `sid`** — filling the HELLO `sid` field the frame already carries and feeding it into the generator, which is precisely the CFRG CPace draft's prescription for this single-flight topology (§3.1, §10.9) at zero extra round-trips, restoring the `sid`-uniqueness assumption the UC-composability proof needs, while keeping CI as a defense-in-depth second binding and naming the human PIN as the real MITM anchor. **D2** resolves Concern #1 in favour of Option B — a **dedicated, separately-generated X25519 identity key** with codebase-wide key separation, rather than converting the Ed25519 signing key for DH. The rejected alternative (birational Ed25519→X25519 conversion) reuses one key for sign and DH with no joint-security proof — XEdDSA §8 explicitly declines to certify exactly this — against the field default of separation (NIST SP 800-57 §5.2, libsodium's FAQ, Noise §14, MLS/RFC 9420's split `signature_key`/`encryption_key`); it is also PQ-forward, since the planned hybrid KEM key is unavoidably separate anyway. The honest framing, preserved in the log: this is risk-aversion plus PQ-forwardness, not a demonstrated break — there is no published attack on Ed25519/X25519 reuse specifically. Both decisions are also *implementation* work, because the shipped `c835244` code had converged on neither.

#### Methodology

Stage 4 extends the Stages 1–3 thread — tests prove the code does what it asserts; a dedicated adversary proves the assertions were the right ones — into the part of the system where a wrong assertion is a live network vulnerability rather than a wrong constant. Of the four review catches, two were security bugs invisible to the green suite that shipped alongside them: the **gate unhandled-rejection** (a correctness/observability defect the 5/5 tests structurally could not see, because they all attached handlers synchronously) and, more seriously, the **DTLS fail-open** — a MITM tripwire that passed whenever it could not read the certificate, rated CRITICAL, caught by asking what `getStats()` returns when the cert stat is *absent* rather than merely *wrong*. In both cases the fix arrived with a regression test that fails for the demonstrated reason before the change and passes after, and each fix commit was independently re-reviewed and re-approved (`4b98c62`, `2af322b`). The two-stage (spec-compliance then code-quality) gate also did adjudication work that is not bug-catching but is just as load-bearing: it ruled the empty-`sid` and send-MAC-first deviations *sound* with reasons on the record, so the no-PIN RangeError could be escalated as a design question (D2) rather than patched over with a raw-key path that would have quietly reintroduced the very key-reuse the codebase is trying to leave behind.

### D2=B — dedicated X25519 identity + codebase-wide key separation

D2 decided the *shape*; this stage builds it. The no-PIN handshake needs an X25519 identity key that is genuinely separate from the Ed25519 signing key, generated and stored and cross-signed and carried to the peer and verified before it is ever used in a DH — and it needs to do all of that without leaving a residue of the one-key-for-two-jobs pattern the decision exists to retire. The work landed as five reviewed, green commits (T1–T4 plus the coupled handshake surgery) and one review-driven wipe fix, on top of a design spec that was itself put through a pre-implementation review that caught a real MITM vulnerability before a line of it was written.

**The generator (`src/cryptography/x25519.ts`, `src/cryptography/memory.ts`, `41de52e`).** Task 1 adds `newX25519KeyPair(module?)` — an async, optional-module wrapper over the Stage-2 `x25519Keypair`, mirroring `ed25519.newKeyPair` so an identity-generation site mints the dedicated random X25519 identity the same way it already mints an Ed25519 one (self-loading a `LibCrypto` module and sizing its own 2 MiB heap when none is passed), plus the `identityX25519KeypairMemory` sizer. Red (missing export) → green, 89/89. No new WASM export was needed — `_x25519_keypair` already exists — which is the concrete cash-out of D2=B declining the conversion path: the birational-map primitive with its documented first-32-of-64-byte silent-truncation footgun is simply never taken.

**The wrapped-IndexedDB identity store (`src/db/*`, `38c2f24`; purge `fc01737`).** Here the stage made a mid-flight decision worth recording: rather than store the new X25519 secret as plaintext hex in `localStorage` (the shape the older Ed25519 identity uses) and then deprecate that path later, Task 2 reuses the Stage-3 at-rest infrastructure *now* — the secret is `wrapSecret`-wrapped under the same non-extractable AES-GCM WebCrypto key (`getWrapKey`) and put in the existing `meta` store under `"identityX25519"` (no dbVersion bump, since `meta` already exists), with the public `pub` and `crossSig` stored in the clear. This is `getIdentityX25519` / `setIdentityX25519` / `deleteIdentityX25519` mirroring the Stage-3 ratchet-session pair, and it buys two things at once: it avoids ever writing a to-be-deprecated plaintext path, and it makes the confusing X25519-vs-Ed25519 hex-length validation in `keyPairSlice` simply *disappear* — there is no plaintext hex secret to validate. The security-load-bearing assertion has teeth: the worker test reads the raw stored record back and asserts the secret field is ciphertext (both longer than, and unequal to, the 32-byte plaintext), so a full DB dump yields wrapped bytes, not the key. 8/8 worker tests, full suite 93/0. Task 3 closes the rotation hole by wiring `deleteIdentityX25519()` into both `purgeIdentity` and `purge` (`src/index.ts`), so a reset or rotated Ed25519 identity never leaves an orphaned X25519 record and cross-signature behind (former risk R5).

**The domain-separated cross-signature and the SECURITY-1 finding (`src/cryptography/identityCrossSig.ts`, `src/utils/constants.ts`, `59b011a`).** For a relying party to trust the separate X25519 key, the Ed25519 identity it already anchors on must vouch for it — a cross-signature `sign(X25519_pub, Ed25519_secret)`. The spec review caught, *before implementation*, that the obvious bare version of this is a genuine MITM vulnerability. `handleChallenge.ts` signs a server-supplied login challenge with this same Ed25519 identity secret, and `handleWebSocketMessage.ts` gates that flow on `challenge.length === 64` hex — exactly 32 bytes, exactly the size of an X25519 public key. So a malicious signaling server sends a *chosen* X25519 pubkey (whose secret it holds) as the "login challenge," harvests `sign(chosen_X25519_pub, victim_Ed25519_secret)`, and now holds a bit-for-bit valid cross-signature binding *its* key to the *victim's genuine* identity — defeating the whole anchoring goal with **no Ed25519 forgery at all**. This is the identical bug class the codebase already fixed once for chunk-auth (the reason `CHUNK_AUTH_DOMAIN_BYTES` exists); the fix is the same medicine. A new SSOT constant `IDENTITY_CROSS_SIGN_DOMAIN_BYTES = "p2party-x25519-idsig-v1"` prefixes the signed transcript — `sign(IDENTITY_CROSS_SIGN_DOMAIN ‖ X25519_pub, …)` — making the cross-sig transcript disjoint from the challenge transcript so no oracle output is ever a valid cross-signature. `sign`/`verify` stay generic; the caller owns the domain label. The regression test is explicit: an oracle-harvested *bare* signature (over the raw pub, as the login oracle would yield) fails `verifyIdentityCrossSig`. Task 4 also wires generation into `signalingServerApi.ts`'s `websocketBaseQuery` as a self-healing step — it regenerates the wrapped X25519 identity whenever the stored record's cross-sig no longer verifies against the *current* Ed25519 identity, covering all four first-run/upgrade/rotate states — at 96/0.

**The handshake surgery: D1 + in-band identity + the double-wrap fix (`src/handlers/handleHandshake.ts`, `d35045c`; wipe `40d97b0`).** Three coupled changes land the decisions into the live handshake. **D1 (initiator-first `sid`):** the deliberate empty-`sid` generator (`CPACE_GEN_SID = new Uint8Array(0)`) is removed, and the generator now binds the *initiator's* 32-byte `sid`. The narrative reversal is the interesting part — the empty-`sid` was never a mistake, it was a correct observation that in a *symmetric* single simultaneous HELLO neither leg can bind the peer's nonce before publishing `Y`; D1's move is to make the flow *asymmetric* instead. The exchange becomes initiator-first (`amInitiator` sends HELLO then receives; the responder receives, parses, then derives `G` over the initiator's `sid` and only then sends), which is the on-spec CPace single-flight shape and lets the responder derive `G` with the initiator's `sid` for free. **T5 (in-band, not the server):** the X25519 pub and its cross-signature ride the HELLO frame itself over the DTLS channel — HELLO grows 97 → 193 bytes — and are verified *before any DH*, fail-closed: immediately after parsing the peer HELLO and before the PIN/no-PIN secret branch (and, for the responder, before it even sends its own HELLO), the core runs `verifyIdentityCrossSig(peerX25519Pub, peerCrossSig, peerIdentityEd25519Pub)` and throws on failure, at which point the existing `catch`/`finally` wipes have leaked nothing and no shared secret was ever computed. This is the "server is a dumb bootstrap" principle made concrete: the signaling server carries only the SDP/ICE needed to open the DTLS channel (which inherently exposes the fingerprint), and every key and cross-signature moves in-band afterward. The no-PIN X3DH now consumes the *verified* peer pub straight from the HELLO, closing the Task-4 RangeError concern at its root.

The surgery also found and fixed a **double-wrap persistence bug** that would have made every persisted session unreadable. `runHandshake` was building the `RatchetSession` by calling `wrapSecret` on each secret field *and* then handing it to `setRatchetSession`, whose worker path (`fnSetRatchetSession` → `wrapRatchetSession`) wraps the secret fields *again* — doubly-encrypted, and so undecryptable on the way back out. The fix builds the session from the plaintext `serializeRatchet` ArrayBuffers and lets the worker do the single, canonical wrap (removing the now-dead `getWrapKey`/`wrapSecret` imports to keep the file lint-clean). It is a quiet but instructive catch: two independently-correct layers — a handshake that wraps its secrets, and a persistence API that wraps what it's given — compose into a silent corruption, and only a test that actually round-trips a session back through `unwrap` exposes it. The surgery closed at 11/11 handshake, full suite 97/97, with a focused security review APPROVED (no Critical/Important). A follow-up review Minor became `40d97b0`: `idSelfSec.fill(0)` — the unwrapped long-term X25519 identity secret — ran only on the success path, so any error (bad cross-sig, key-confirm fail, DTLS/lookup throw, persist reject) left it in the JS heap; both `idSelfSec` and the root `secret` are now hoisted and wiped in a `finally`, so they clear on every exit.

#### Methodology

The D2=B stage is the strongest single data point for the "review as a safety net" thread the whole rewrite has been building, because the most valuable catch happened at the *design* layer, before implementation had a line to test. SECURITY-1 — the cross-signature oracle — is a real MITM vulnerability (a malicious server binding its own key to a victim's identity with no Ed25519 forgery), and it was found by a pre-implementation review of the D2=B spec, then closed by construction with a domain prefix and pinned by a regression test that a green functional suite would never have thought to write, since a bare cross-sig *works perfectly* in every honest test. Alongside it, the code-layer reviews caught the double-wrap (a silent-corruption bug where two correct layers compose wrongly) and the incomplete secret-wipe on the error path — neither of which any passing test asserted. Set against the Stage-1/2/3 tally (the unrealizable nonce, the CPace transcript ambiguity, the unwiped DH secret, the X3DH blind spot, the ratchet replay-desync) and the Stage-4 catches (the gate unhandled-rejection, the DTLS fail-open), the pattern is now unambiguous and is the paper's methodological argument: the failures that matter most — the ones that are latent security bugs rather than style — are precisely the ones a green test suite is, by construction, unable to see, and a dedicated adversary applied per task (and, for the hardest calls, per *spec*) is what surfaces them while they are still cheap to fix.
