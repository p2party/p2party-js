# p2party desync hunt — adversarial verification of 35 candidate findings

SDK `p2party-js` @ `3c7f169`, `p2party-server`, `p2party.com`. 35 findings → **11 CONFIRMED clusters, 6 PARTIAL, 1 refuted, 17 folded as duplicates.** Every file:line was re-checked in source.

## 1. Verdict: does the fixed bug class have remaining members?

**Yes — two.** The class is "one side holds a stale-but-connected `RTCPeerConnection` while the other can no longer be signalled, and nobody re-dials". 0.14.5–0.14.7 closed every *transport-observable* entry (DTLS cert change, grace teardown, lost first offer, stalled rebind, heartbeat watchdog). Both survivors enter through the **signaling socket**, where no transport event fires. **C1**: the server evicts a predecessor socket when one identity connects twice (second tab, or a phrase-restored second device); the peer's edge stays bound to the evicted side, and since the protocol *responder* creates no data channel on a fresh transport it can never offer, so the new session never gets an edge. **C4**: any socket close not accompanied by a browser wake event is terminal — the SDK has exactly two `connectWebSocket` call sites (`index.ts:332`, the public API; `handleConnectToPeer.ts:176-181`, reachable only from an ICE failure), and the site's auto-connect is one-shot per room URL. The other nine clusters are outside the class: four scheduled-cover defects, two transfer-resume data-loss bugs, an author-acknowledged re-dial loop, and two roster gaps that appear only at n≥3.

## 2. CONFIRMED clusters (severity, then confidence)

### C1 — Same identity on a second socket: the responder can never bootstrap an edge *(0, 9, 12, 16, 18, 24; +1, 17)* — HIGH / 0.9
- **Trigger.** One identity opens the room in a second tab or a phrase-restored second device while the first holds an authenticated edge to B, **and** is the protocol responder (Ed25519 hex lexically greater — 50% of pairs). No tab lock exists: `navigator.locks`/`BroadcastChannel` have zero hits in either `src` tree; both tabs adopt the stored key (`signalingServerApi.ts:200-220`). `p2party-js/README.md:99-101` tells users to open the demo in two tabs of one origin.
- **Mechanism.** Server `handleConnection.ts:21-30` upserts `Peer` by `publicKey`, so T2 gets the *same* peerId; `socketAuth.ts:197-206` sets `clients[peerId]=T2` and calls a bare `predecessor.close()` — **no close code, nothing broadcast to the room** (`publish()` at `wsServer.ts:160-161` has zero callers). T1's `settleClosedSocket` (`signalingServerApi.ts:409-427`) dispatches `disconnect()` only; the handler takes no event argument, so the code is never read — PC#1 and its ratchet are untouched. T2 runs `connectWithPeer(B)` → `baseQuery.ts:68` `opensMain = isIdentityInitiator(self, peer)` (`identityRole.ts:26-35`: `self < peer`). As responder `opensMain` is false ⇒ `baseQuery.ts:114` never calls `openMainChannel` ⇒ no channel ⇒ `onnegotiationneeded` never fires ⇒ **no offer, ever**. The codebase asserts this at `setDescriptionQuery.ts:168-177` and `pendingOffer.ts:21-23`; no other `createDataChannel` can fire on a fresh responder PC (`coverEdge.ts:92` is post-handshake, `setDescriptionQuery.ts:475-491` is gated on `isIdentityInitiator`, `openChannelQuery` has no live caller). B receives T2's `connection` frame → `connectionSignal.ts:35-40` → `baseQuery.ts:79-93`: PC#1 is neither `closed` nor `failed`, so it **early-returns**. Nothing watches PC#2 — the offer watchdog needs `have-local-offer` (`pendingOffer.ts:31-34`), the rebind deadline is armed only from `remoteTransportChange.ts:347`, the 8 s grace needs ICE to have run, `applyIceConfiguration.ts:8-9` skips description-less PCs. T2's reconciler fires 8× (5/10/20/40/60 s, `constants.ts:286-289`) against an identical server answer, then retires keeping the entry with no timer (`roomRosterReconciler.ts:119-125`).
- **End state.** B: roster [A] `authenticated`, PC#1 pointing at the socket-less T1; sends land there and report delivered. T2 (visible tab): verified socket, roster [B] with no handshake status, one PC in `new` with zero channels; sends fail at 12 s (`PEER_ADMISSION_WAIT_MS`) or 45 s (`RATCHET_GATE_WAIT_TIMEOUT_MS`). T1: authenticated edge, no socket. Nothing happens for 5 minutes. With TURN configured it self-heals at **≈55 min** (B's refresh restarts ICE, its offer routes to *T2's* socket, T2 answers with a fresh cert, B's `decideRemoteTransportChangeResponse` → `"replace"`). STUN-only self-host: no refresh timer is installed (`roomRequestCoordinator.ts:409`) — **unbounded**.
- **Sub-mechanism (1, 17), confirmed.** `ensureFreshIceConfiguration` (`handleConnectToPeer.ts:176-181`) dispatches `connectWebSocket` whenever `!isConnected && !isEstablishingConnection`, so any ICE blip on the *hidden* tab's edge re-takes the identity and evicts the *visible* tab — which has no trigger: `focus` does not fire in an already-focused tab, and `autoConnectAttemptedRoomRef` (`ChatLayout.tsx:68`) blocks the effect even though `isConnected` is in its deps.
- **Missed because** every landed fix replaces a transport on a fingerprint change in an SDP, an ICE/grace failure, an unanswered first offer, or a stalled rebind. B receives no SDP, its transport never fails, no rebind occurs. The reconciler (5185f06) fires, but the server re-introduces the *same peerId*, which B reads as "already connected". `socketAuth.test.ts:93-117` pins only that the predecessor is closed; nothing opens two sockets for one publicKey.
- **Fix.** Make the socket generation part of edge identity. `p2party-server/src/utils/socketAuth.ts`: carry a per-socket generation (`ws.data.challengeId` is already fresh per socket) in the `peerConnection`/`peers`/`connection` introductions. `p2party-js/src/api/webrtc/baseQuery.ts:79-93`: record it on the `IRTCPeerConnection` and treat a changed generation for one peerId exactly as `remoteTransportChange` treats a fingerprint change (retire → `disconnectPeer` → rebuild → re-dial). Cheap mitigation: tear down a responder PC still in `new` with no remote description after `PENDING_OFFER_TIMEOUT_MS`.
- **Harness.** `docs/e2e/desync/relay.ts` already models the eviction (`RELAY_PEERID_MODE=stable`) and exposes `GET /ctl/registry`. Add `two-tabs` to `desync-driver.mjs`: T1+T2 in **one** Chromium context (shared IndexedDB ⇒ same identity) plus B in a second, keys chosen so B's hex < A's. Connect T1+B, assert I2, then connect T2. At 60 s and 5 min assert: registry shows A's socket replaced; B has one PC whose remote fingerprint is T1's; T2 has one PC, zero channels, no `handshakeStatusByPeer`; T2's `sendMessage` rejects at ~45 s. Close T1 → B↔T2 authenticate in ~15 s. Re-run with A's hex < B's and assert ~5 s convergence via the `replace` path.

### C2 — A terminal handshake failure re-dials anyway through `main.onclose` *(7, 11, 8)* — HIGH / 0.9
- **Trigger.** One wrong PIN character; or two members holding different immutable room policies (a pre-`pq` invite vs. a current one), which fails the *framing* check instead.
- **Mechanism.** The catch (`handleOpenChannel.ts:939-952`) classifies by **regex on the error message** and re-dials only for `"transport"` (`:1000-1001`); the intent is verbatim at `:996-999`: *"a PIN or policy mismatch fails again on any fresh transport and a re-dial would only burn another attempt against the PIN throttle."* But it closes the channel with handlers **still attached** (`:992-993`), unlike the SDK's own teardown, which nulls them first (`disconnectFromPeerQuery.ts:150-157`). The `close` event fires `main.onclose` (`:393-422`), whose only guard is `isCurrentRatchetGateLease` — and `rejectRatchetGate` (`ratchetGate.ts:102-119`) sets `settled`/`outcome` but **never replaces `gate.lease`** (only `resetRatchetGate:121-135` mints a new one), so the check passes. `onclose` then runs `disconnectFromPeer` and `requestPeersAfterEdgeTeardown` (`:422`) unconditionally — a helper that "has no backoff of its own" (`edgeTeardownFollowUp.ts:32-33`), limited only by a 2 s per-room min-interval (`signalingPeerRequestDebouncer.ts:13-25` is a debounce, not a budget). Both sides fail key-confirmation by construction, so both rebuild PC + ICE + DTLS + `main` every ~3–5 s. A pq-suite mismatch is rejected by the framing check (`handleHandshake.ts:239-250`), matches neither regex, is classified `"transport"`, so the **catch itself** re-dials forever, never reporting `"policy"`. Field corroboration: the 0.14.7 changelog notes a rejected joiner is "dropped from the roster before the app can attach the failure to anyone" — only this `onclose` does that.
- **End state.** Both sockets verified; rosters flip `[peer] → [] → [peer]` every few seconds. PIN backoff escalates to `PIN_BACKOFF_MAX_MS` = 300 s over ≈8.5 min of real attempts (throttled iterations record nothing). `clearPinAttempts` (`index.ts:427-431`) is a local IndexedDB delete, so correcting the PIN leaves the honest peer throttling up to 5 more minutes. For a policy mismatch: **never converges**.
- **Missed because** b4005fd classifies by *who tore down*, and a handshake-terminal close is neither — the catch does not own its teardown. The regression test is vacuous: `tests/handlers/handleOpenChannelRedial.test.ts:101-104` uses a fake whose `close()` flips `readyState` without dispatching a `close` event, so ":293-340 (a PIN-throttled failure does not re-dial)" passes while the browser does exactly that; ":342-361" pins the `onclose` re-dial as unconditional.
- **Fix.** `handleOpenChannel.ts`: for `pin-mismatch`/`pin-throttled`/`policy`, null `extChannel.onclose`/`onerror` before closing (mirroring `disconnectFromPeerQuery.ts:150-157`), or set `epc.handshakeTerminalFailure` for `:393-422` to consult. Return a typed reason from `deliverHandshakeFrame` instead of regexing the message. Make the test fake dispatch the event.
- **Harness.** `docs/e2e/desync` supports `mode:"pin"`. Add `pin-typo`: A with the right PIN, B with a wrong one; over 120 s assert B's PC id increments >10× and `pinBackoffMs` climbs, then supply the correct PIN and measure time-to-authenticated.

### C3 — `SCHEDULED_DELIVERY_TIMEOUT_MS` is shorter than one receipt round trip on shipped presets *(5, 34)* — HIGH / 0.9
- **Trigger.** Any `sendMessage` in a "5 min cycles" room (100% of sends); a send in the first ~0.5–1.4 s after a boundary on the default "60 s" preset (0.8–2.3%).
- **Mechanism.** `SCHEDULED_DELIVERY_TIMEOUT_MS = 120_000` (`handleSendMessage.ts:1312`) is fixed and unrelated to the room policy. Jobs are admitted **only at a cycle open** (`coverScheduler.ts:592-599` is the sole `dequeue()` site), so a job enqueued at `t` first sends at `B1=(k+1)T`; the receiver's terminal receipt (queued only on `receivedFullSize`, `handleMessageQueueing.ts:380-386`) is itself a job admitted at `B2=B1+T`. With `T`=300 s (`p2party.com/src/protocol/v4.ts:104`) the minimum confirmation is **301.2 s**. On timeout `handleSendMessage.ts:1288-1289` zeroes `stepped.messageKey` and `pqContext.rootKey` **unconditionally** — the same arrays the sealer closure at `:1254-1265` still holds — and `:1485` deletes the staged chunks, after which the still-admitted job emits dummies. No CANCEL reaches the receiver: `cancelScheduledTransfer` (`coverTransfer.ts:211`) has **zero `src/` callers**, `buildScheduledSendJob` (`:186-201`) defines **no `cancelCell`** so `scheduler.cancel` would throw (`coverScheduler.ts:313-316`), an inbound CANCEL only reaches sender-side registries (`transferAbort.ts:152-181`), and a cover-lane close is never a cancel (`handleOpenChannel.ts:370-391`).
- **End state.** Sender: `MessageDeliveryError`, local copy kept, staging gone, key zeroed. Receiver: either a **complete** message the sender calls failed, or a partial stuck at n/N forever — a re-send cannot fill it because decoy chunks are fresh randomness (`splitToChunks.ts:226`) so the Merkle root differs. Multi-peer rooms serialize 120 s per failing target (`:1218-1308`); immediate mode fans out un-awaited (`:774-788`).
- **Missed because** the constant predates 0.14.5 and nothing in range touched it. No test runs a send at ≥10 s cadence (fixtures use 400 ms); the desync driver connects with `{}` = immediate (`desync-driver.mjs:361-362`).
- **Fix.** `handleSendMessage.ts:1312`: derive the bound from the schedule (`≥ 2 × cycleDurationMs + spacing + margin`) or settle from the job via `onJobResult`. Do not zero the key or delete staging until the job is cancelled — implement `cancelCell` and call `cancelScheduledTransfer` from the failure path. `src/roomPolicy.ts:69-70` allows a cadence up to 1 h with no cross-check.
- **Harness.** Parameterise `docs/e2e/appstack/app-driver.mjs`'s scheduled arm to the three presets: 5 min → sender rejects at ~120 s, receiver shows nothing or a frozen partial; 60 s fired 0.3 s after a boundary → receiver byte-exact, sender rejects.

### C4 — A socket closed without a wake event is terminal *(26, 29; server triggers 15)* — HIGH / 0.9
- **Trigger.** A signaling deploy (`deploy/ansible/playbooks/deploy.yml:250-252` restarts every unit; shutdown sends no close code, so clients see a bare 1006); the 25 s heartbeat watchdog tripping on an outage that never flips `navigator.onLine`; or any server-side close on an innocent peer — `handleMessage.ts:283-287` closes on **any** thrown error, `findRoomPeers.ts:103-107` `ws.terminate()`s on a caught DB error, and `handlePeerAcceptsConnection.ts:43-59` **closes the acceptor's socket** when the introduced joiner has already left, where the sibling `handlePeerConnection.ts:43` drops the same condition silently.
- **Mechanism.** `settleClosedSocket` (`signalingServerApi.ts:409-427`) dispatches `disconnect()` and nothing else — no backoff, no retry, no close-code inspection. The heartbeat watchdog (d2e52e3) routes to the same function: it *detects*, it does not reconnect. `requestPeersAfterEdgeTeardown` returns false without a socket (`edgeTeardownFollowUp.ts:46`); `isRoomRosterStranded` returns false without a socket (`roomRosterReconciler.ts:179`). The site reconnects only on focus/visibilitychange/pageshow/online (`ChatLayout.tsx:126-129`); its auto-connect is gated by `autoConnectAttemptedRoomRef.current !== roomUrl` (`:68`), set on first success and cleared only on failure — so although `isConnected` **is** in the effect's deps and the effect re-runs on `true → false`, the ref blocks it every time. A focused desktop tab **never reconnects**. `edgeTeardownFollowUp.ts:22-24` asserts "the signaling reconnect path re-requests the roster on its own" — that path does not exist.
- **End state.** The peer: `isConnected=false`, no timer, existing edges still authenticated and passing messages, so no ICE event prompts a repair. Server: still a durable member with `serverId=null` (`wsServer.ts:73-86` prunes no membership); every introduction toward it is dropped (`pubsub.ts:230`). A later joiner's reconciler retires after ~5.25 min having achieved nothing. Indefinite.
- **Missed because** the harness masks it: `desync-driver.mjs:603` emulates the focus handler after **every** non-baseline fault, so the recorded `ws-drop +0 s` pass is driven by an event a foreground client never gets.
- **Fix.** `signalingServerApi.ts:409-427`: on any close the SDK did not initiate, schedule a bounded backoff reconnect (1/2/4/8/15/30 s) while some room has `signalingActive`. This one change also retires the consequence half of findings 15, 27 and 28. Server: `handlePeerAcceptsConnection.ts:57` should drop silently like `handlePeerConnection`, and `findRoomPeers.ts:104` should return false rather than terminate.
- **Harness.** Add `ws-drop-nofocus`: identical to `ws-drop` but **skip** the `focusReconnect(A)` at `:603`. Assert A stays disconnected for 120 s, then boot a third page C into the room and assert C's roster stays empty through its full reconciler budget.

### C5 — A late boundary timer parks the cover scheduler in `suspended` forever *(4, 32)* — HIGH / 0.85
- **Trigger.** Any main-thread stall >311 ms (10 s preset) / >500 ms (60 s, 5 min) overlapping a due `cycle-boundary` or `open-boundary` timer, tab visible.
- **Mechanism.** `maxTimerDriftMs = min(floor(slotSpacing)−1, 500)` (`coverRuntime.ts:166-169`). On overrun (`coverScheduler.ts:526-529`) `handleLateTimer` (`:557-573`) degrades for `kind==="slot"` but for boundary kinds calls `setStatus("suspended","timer-drift")` and **arms nothing**, while `this.running` stays true. `resume()` (`:367`) is the only exit; `degrade()` (`:829`), `suspend()` (`:351`), `start()` (`:337`) all early-return while suspended and `openCycle` (`:579-585`) refuses. `resume()` has three callers: `coverRuntime.ts:245` (a public method with **zero callers in `src/`**), `:422` visibilitychange→visible, `:438` online. No periodic self-check. Exposure far exceeds a boundary instant: `degrade()` arms a cycle-boundary timer for the **whole remainder** (`:837-839`), and degradation is routine because every boundary opens brand-new lanes (`coverEdge.ts:91-95`) that may not be `open` at the first slot; `resume()` on a phone wake arms an open-boundary timer up to a **full cycle** ahead (`:379`), exactly while the page is thrashing. `realClock.now` is `Date.now()` (`coverRuntime.ts:97-101`), so an OS suspend or NTP step also trips it. Two further unrecoverable routes the findings missed: the handler-rejection catches at `:530-533` and `:911-913`.
- **End state.** Both sides `authenticated`, PC `connected`, `coverStatusByPeer="suspended"/timer-drift`, scheduler running with no timer. Every send in **both** directions fails after 120 s (the peer's receipt job is queued forever too). The site renders "cover gap — not sending" (`CoverStatusPill.tsx:35`) and acts on nothing. Indefinite.
- **Missed because** `git log 4432feb..fcdbb31 -- src/handlers/coverScheduler.ts` is empty; the only `coverRuntime.ts` change in range (42d6758) is comment-only. `coverScheduler.test.ts:333-355` covers a late *slot*. The runtime's own comment (`coverRuntime.ts:162-165`) claims a larger slip "still degrades" — the code suspends.
- **Fix.** `coverScheduler.ts:557-573`: for non-slot kinds close the late cycle, `setStatus("degraded",…)`, then `if (this.running) this.armOpenBoundary(this.nextCycleBoundary(now,false))`. Same for `:530-533`, `:911-913`. Make `sendScheduled` fail fast when the runtime is `suspended`.
- **Harness.** Connect both `docs/e2e/desync` pages with `mode:"scheduled"` (implemented at `app-entry-desync.ts:153-176`, never driven) at the 10 s preset. Force one degraded cycle, then run a 1.5 s busy-loop spanning the next boundary. Assert `suspended` persists 3 min and sends both ways reject at ~120 s while both handshakes stay `authenticated`.

### C6 — Sparse-PQ healing strands an in-flight scheduled transfer *(31)* — HIGH / 0.85
- **Trigger.** The 64th message on an edge (`PQ_HEAL_AFTER_MESSAGES`, `pqHealingRuntime.ts:59-60`) or 24 h, landing mid-transfer. **No fault, no network event, no second device.**
- **Mechanism.** The quiescence gate is `(epc.messageChannels?.size ?? 0) === 0 && !hasQueuedEdgeReceiveWork(...)` (`pqHealingOrchestrator.ts:112-117`). Scheduled lanes register in `epc.coverChannels`, never `messageChannels` (`handleOpenChannel.ts:242-269`; outbound `coverEdge.ts:91-118`), and the orchestrator/runtime contain **zero references to `coverRuntime`/`coverChannels`** — so an edge saturated with scheduled cells reads as quiescent and the 1 s tick (`:261-272`) starts an epoch advance. The damaging asymmetry: cover dummies and receipts seal against the **live** context (`coverRuntime.ts:349-366` reads `pq.currentMessageContext()` at seal time), but a real chunk cell's `pqContext` is **frozen at ratchet-step time** (`ratchetPersist.ts:409-417`; `handleSendMessage.ts:1254-1265` hands it to the sealer, used at `:1189` for every later slot) and lands in the wire header (`messageChunkCrypto.ts:257-261`). On the receiver `resolveMessageContext` is exact-match (`pqHealingRuntime.ts:664-669`) and runs at `messageChunkCrypto.ts:354-370` — **before** the key-cache lookup at `:372-392` — so once `commitAcceptedAdvance` (`:851-880`) retires epoch N, every remaining cell is rejected and even a cached key is unreachable.
- **End state.** Both sides `authenticated`, cover `active`, epoch N+1; remaining cells dropped silently; the sender fails at 120 s with no CANCEL; the receiver keeps an unfillable partial. Permanent — the only receive-side `deleteReceiveTransfer` is behind an explicit user `deleteMessage` (`roomListenerMiddleware.ts:411-426`), and the OPFS file stays pre-sized to `totalSize` (`db/db.worker.ts:1070-1074`).
- **Missed because** 0.14.5–0.14.7 are transport fixes; this is a crypto-epoch/scheduling interaction on a healthy edge. Commit 42d6758 established that PQ *control cells* never ride cover lanes — a different claim that says nothing about the *epoch of real chunk cells*.
- **Fix.** `pqHealingOrchestrator.ts:112-117`: extend `isEdgeQuiescentForHealing` to `epc.coverRuntime === undefined || no admitted/queued real job`, exposing `hasPendingRealJobs()` from `coverScheduler`. Alternatively re-seal remaining cells against the live context on an advance, or let `resolveMessageContext` accept the immediately-retired epoch for an in-flight transfer's lifetime.
- **Harness.** `docs/e2e/appstack` scheduled arm at the 10 s preset: send 63 small messages, then start a multi-chunk transfer and let the 64th trip healing mid-flight. Assert the receiver reaches N/N and the sender resolves.

### C7 — A resumed channel's own pre-auth close is read as a peer CANCEL *(21)* — HIGH / 0.85
- **Trigger.** Any mid-transfer edge replacement where the **receiver is the identity responder** and the sender's ratchet persist is slower than the receiver's persist plus its leaf-hash scan — e.g. sender on a phone, receiver on a desktop.
- **Mechanism.** `resumeChannel` (`handleSendMessage.ts:410-415`) selects a PC on `connectionState === "connected"` alone — DTLS-complete, *before* the main-channel handshake — and calls `handleOpenChannel` at `:431` with no gate await. The receiver's inbound onopen (`handleOpenChannel.ts:1023-1050`) waits only for its **own** gate, then replays receipts. Gates open independently inside an async IndexedDB persist (`handleHandshake.ts:482-494` → `ratchetPersist.ts:200-225`), and the responder completes on *sending* FINISH (`handshakeCore.ts:762-763`) while the initiator completes on *receiving* it (`:803-807`). The latency terms cancel: the condition is exactly **`P_R + scan < P_S`**. When it holds, the receipt hits the sender's guard at `handleOpenChannel.ts:556-566`, which **closes** rather than parks (`isRatchetGateOpen`, `ratchetGate.ts:77-87`, cannot distinguish pending from rejected). The sender's gate then opens and `isAuthenticatedPeerCancel` (`:615-630`) returns **true** — connected, lease current, PC registered — because no `closedLocally` marker exists anywhere (`grep closedLocally src/` → zero hits). The sender throws "Message transfer cancelled by peer"; the receiver's onclose (`:444-461`) reads `isRemoteCancelClose` and runs `cancelReceiveTransfer` → `deleteReceiveTransfer` → `disconnectFromPeerChannelLabel({alsoDeleteData:true})`.
- **End state — bilateral data loss on a healthy edge.** Receiver: every chunk including all pre-outage progress, its `messageData` row, the OPFS file and the Redux message are deleted. Sender: `deleteDBNewChunk` (`:1485`) removes the only resend source; the tracker shows "failed: cancelled by peer" although the peer cancelled nothing. Both PCs stay connected and authenticated, so no teardown, re-dial or reconciler ever fires. Terminal.
- **Window (honest).** Two conditions: `P_R + scan < P_S` (the common case on asymmetric hardware; OPFS/bytesless chunk records make `scan` nearly free), and the resume poll (`RECONNECT_RESUME_POLL_MS = 500`) landing within `2L + max(P_R,P_S)` of `connected` — roughly **10–40% per resume event** on a real network, near zero on loopback with two identical machines.
- **Missed because** abcf267/f7b0d5c made the cancel classifier lease-aware for the *retired* generation; here the closed channel carries the **current** lease and was closed by this side's own guard, so every check legitimately passes. `resumeChannel` is not exported and has zero test references; the harness's recorded "151/151 real chunks, **0 retransmits**" (`docs/e2e/README.md:266-267`) proves `resumeChannel` never succeeded in any recorded run, since the counter is bumped on both the resume and reconcile paths.
- **Fix.** (1) `resumeChannel`: await a bounded `waitForRatchetGate` **before** `handleOpenChannel`; on timeout treat it as "no usable PC" and keep polling. (2) `handleOpenChannel.ts:556-566`: when the captured lease is current and the gate is merely *pending*, park the frame until it resolves (as `handleMessageQueueing.ts:339-343` already intends) and keep the close only for a stale lease or rejected gate. (3) Record `closedLocally` in the guard's close path and have `isAuthenticatedPeerCancel` consult it.
- **Harness.** Extend `proc-freeze-20 --transfer` so the freeze lands **mid-transfer** with the receiver as identity responder, plus an artificial sender-side persist delay (~50 ms) via a page hook. Assert the sender resolves and the receiver's chunk count only ever increases.

### C8 — An in-flight scheduled send dies with the cover runtime on every landed recovery path *(6, 22, 33)* — HIGH / 0.8
- **Trigger.** Any recovery 0.14.5–0.14.7 made fast — cert-change replace, in-place rebind, grace teardown, ICE failure, re-dial — while a scheduled transfer is in flight.
- **Mechanism.** `teardownCoverEdge` (`coverEdge.ts:54-65`) calls `runtime.destroy()` → `coverRuntime.ts:225-234` → `scheduler.stop()` (`coverScheduler.ts:387-411`), settling every job `failed/stopped` and deleting it from the map (`:470-478`). It is called from all four recovery paths: `baseQuery.ts:101`, `disconnectFromPeerQuery.ts:89-90`, `remoteTransportChange.ts:306-307`, `setDescriptionQuery.ts:300`. The replacement runtime starts empty and nothing re-enqueues: `installCoverEdge` (`coverEdge.ts:78-131`) passes no `onJobResult`/`onJobInterrupted`, and `trackScheduledSend`'s registry is a `WeakMap` keyed by the old `epc` (`:31-34`). `sendScheduled` has no resume loop — contrast `sendWithReconcile` (`:961-1097`), which f7b0d5c taught to resume across a retired generation — and it awaits `waitForCompletion`, a 200 ms poll of *transfer completeness*, so the settlement is invisible and it blocks the full 120 s. `releaseScheduledReceipts` (`coverTransfer.ts:114-124`) additionally wipes a receiver-side terminal receipt pending at fault time, so even a fully-arrived message goes unconfirmed.
- **End state.** Both sides re-authenticate in 2–12 s and look perfect; the sender hangs 120 s then rejects with staging deleted; the receiver keeps an unfillable partial forever.
- **Fix.** `coverEdge.ts`: pass `onJobInterrupted` from `installCoverEdge` and re-enqueue keyed by `(roomId, peerId, merkleRoot)`; give `sendScheduled` the bounded resume loop `sendWithReconcile` has. **Caveat:** `getAckedChunks` is dead in scheduled mode (`handleMessageQueueing.ts:376` emits per-chunk receipts only when `!epc?.coverRuntime`), so a naive re-enqueue would re-send every chunk.
- **Harness.** Add `--mode=scheduled` to `desync-driver.mjs`'s `connect()` calls and run `proc-freeze-20 initiator --transfer=…`. Assert the sender resolves and the receiver reaches N/N.

### C9 — Introductions dropped silently in the server's ping-to-pong window *(13, 19)* — MEDIUM / 0.8
- **Trigger.** Any join into a room with ≥2 connected members while a member's 10 s ping is in flight; ≈ RTT / 10 s per gated frame. No fault injection.
- **Mechanism.** `handlePeers.ts:111` sends the introduction only `if (peerWsClient.data.isAlive && …)` — **no else branch**: no log, no queue, no error. Same gate on the return leg (`handlePeerAcceptsConnection.ts:97`). `handleInterval.ts:18-21` sets `isAlive=false` the moment each ping is written; `handlePong.ts:58` sets it true on the pong. `sendToPeer` (`pubsub.ts:200-211`) does **not** check it, so the gate is not a transport requirement. The `peers` reply to the requester is commented out (`handlePeers.ts:125-131`), so the joiner never learns who else is in the room, and `isRoomRosterStranded` (`roomRosterReconciler.ts:184-186`) is per-room — with one good edge nobody is stranded and `roomListenerMiddleware.ts:109-110` cancels the backoff on the first authentication. **Extra consequence the findings missed:** the "empty roster → ask again in 5 s" retry at `handleWebSocketMessage.ts:476-503` is dead code, because with the requester reply commented out and `handlePeerAcceptsConnection` always sending exactly one peer, the server can never emit a zero-length `peers` frame.
- **End state.** A and C are live verified members, both authenticated with B, neither listing the other. Heals at the earlier side's TURN refresh (≤ ~55 min) or an unrelated edge teardown; **on a STUN-only self-host, never.** Every server test fixture sets `isAlive: true` — `grep "isAlive: false" src/` returns zero hits.
- **Fix.** Drop the `isAlive` conjunct at `handlePeers.ts:111` and `handlePeerAcceptsConnection.ts:97` (the pong timer already evicts dead sockets). Better: restore the commented-out `peers` reply so the joiner can dial every member and the client reconciler can become per-member.
- **Harness.** Add `POST /ctl/stallpong?pub=…&ms=N` to `docs/e2e/desync/relay.ts` (which mirrors the gate at `:365`) and an n=3 arm: B and C authenticated, A joins while C's pong is stalled. Assert A↔C never forms.

### C10 — Resume-budget exhaustion orphans the receiver's partial *(23)* — MEDIUM / 0.8
- **Trigger.** A receiver unreachable ~40–48 s mid-transfer (8 s grace + 2–10 s + `RECONNECT_RESUME_TIMEOUT_MS` = 30 s, `constants.ts:210-212`) — a phone in a pocket.
- **Mechanism.** `handleSendMessage.ts:1014` `if (!resumed) break;` exits on the **first** null resume (not after 3 attempts) → `:1098-1099` throws "Message transfer ended without receiver confirmation" → `runWithTerminalChannelClose` (`:1102`) closes `currentChannel`, still the **old** dead channel (`:1019` only reassigns on success), so **no frame and no close reach the receiver**; the teardown already nulled every handler (`disconnectFromPeerQuery.ts:142-159`). `finally` at `:1485` deletes the staging.
- **End state.** Both sides re-authenticate and look healthy. The receiver's message sits at N% forever with a `totalSize`-byte OPFS file (`db.worker.ts:1070-1074` — a 2 GB transfer at 5% holds 2 GB on disk). The only thing that would touch it is an inbound channel with that label (`handleOpenChannel.ts:1023-1027`), which the sender will never open again. No age or no-progress pruning exists.
- **Distinct from the accepted residual.** `docs/HANDOFF.md:2144-2146` accepts only "no sender-side resume across a page reload… a reloaded receiver *does* resume". Here the sender's page never reloads, and that consolation is void by construction: the receiver's resume is *reactive*.
- **Fix.** `handleSendMessage.ts`: on budget exhaustion persist a resumable outbox entry instead of `deleteDBNewChunk`, or emit an explicit CANCEL once the edge re-authenticates. Add a receive-side sweep for `savedSize < totalSize` transfers with no progress for N hours.
- **Harness.** Run `proc-freeze-60 --transfer` (the existing 45 s freeze, run 971, carried no transfer). Assert what the receiver holds after both sides re-authenticate.

### C11 — Per-edge loss is invisible to the room-level reconciler *(10)* — MEDIUM / 0.75
- **Trigger.** n≥3, then either (i) a *fresh* A–C transport fails ICE on both sides during a rebuild, or (ii) a correlated blip tears down two of A's edges within the 2 s `redial` debounce.
- **Mechanism.** (i) `handleConnectToPeer.ts:464` re-dials only `if (wasConnected)` (set at `:471-472`) — deliberate and symmetric; the offer watchdog cannot cover it because an ICE-failed transport *has* a remote description (`pendingOffer.ts:31-34`). (ii) `signalingPeerRequestDebouncer.ts:19-24` **drops** a second `redial` within 2 s with no pending flag and no flush, and the roster round that did go out reuses A's still-`disconnected` PC because `baseQuery.ts:79-93` rebuilds only on `closed`/`failed`. Then `isRoomRosterStranded` is false for both A and C, and `roomListenerMiddleware.ts:109-110` cancels any backoff. `deletePeer` removed the row, so A has no record C exists, and the server pushes nothing unsolicited.
- **End state.** A and C are live members, both authenticated with B, mutually absent. Indefinite — heals only on an unrelated edge's ICE repair, a socket reconnect, a TURN refresh, or a reload.
- **Fix.** `roomRosterReconciler.ts`: track the peerIds the server has named for the room and treat a known member with no edge for N seconds as stranded even when others are authenticated. Flush a debounced `redial` at the end of its window instead of dropping it.
- **Harness.** n=3 arm with `POST /ctl/blackhole` on the A–C pair for 12 s; assert A and C keep B and never re-acquire each other within 5 min. (`docs/HANDOFF.md:2163` concedes "The freeze harness is n = 2 on loopback".)

## 3. PARTIAL clusters

- **P1 — TURN expiry restarts ICE with the socket down** *(2, 30; medium)*. Mechanically confirmed end to end: `roomRequestCoordinator.ts:623-625` calls `timer.expire()` on `disconnect`; the callback (`handleWebSocketMessage.ts:301-331`) has **no socket-state check** and restarts ICE on every negotiated PC (`applyIceConfiguration.ts:59-61`); the offer cannot be sent, the catch only `console.error`s (`handleConnectToPeer.ts:320-324`), and no rollback exists (`"have-local-offer"` is read only by `pendingOffer.ts:34`). Production **does** issue TURN (`signaling.env.j2:19,26`; a live coturn host in terraform state), so every production edge is one socket drop from it. **Downgraded because it self-heals**: the PC keeps carrying data on the old pair and the next ICE event reaches the 8 s grace teardown — ~11–15 s typically, ~40 s+ in the frozen-peer + impolite case. It silently converts the ~2 s in-place repair into a full rebuild and makes `repairIce` report `"restarted"` when nothing restarted. Not a persistent split.
- **P2 — `setCandidateQuery`'s ICE repair deadlocks the ingress queue** *(3; low)*. Circular wait confirmed: `setCandidateQuery.ts:97` → `iceRepair.ts:25` → `handleConnectToPeer.ts:198`, whose reply is queued behind the still-running candidate task (`signalingIngressQueue.ts:147-157`; only leave-acks and heartbeats bypass). Resolves deterministically at 15 s, so not persistent — but any room member can impose it at will (`signalingBounds.ts:23-37` never validates `sdpMid` against the local m-sections), and a 15 s freeze can overflow the 128-frame ingress cap, closing the socket with 1008 — which chains into P1 and C4.
- **P3 — Roster written before admission** *(20; low)*. Confirmed and slightly worse than reported: `handleWebSocketMessage.ts:468-474` dispatches `setPeer` for every merged entry, blacklist at `:524-529`, address book at `:531-539`; all three `deletePeer` dispatchers derive their peer list from `peerConnections`, so even the exported `disconnectFromRoom` cannot clear a phantom — only `purgeRoom` or a reload can. PARTIAL because the end state is cosmetic plus a wasted reconciler budget: send targets come from `channels[].peerIds` (`handleSendMessage.ts:1379-1381`), not `room.peers`.
- **P4 — `handlePeers` does one DB round trip per historical member inside the requester's serial queue** *(14)*. Mechanism unambiguous (`handlePeers.ts:116-121` → `pubsub.ts:225-228`; `socketMessageQueue.ts:48-55` closes with 1013); membership is add-only (`handleRoom.ts:71-80`). Trigger weak: needs hundreds of historical identities *and* enough live members to emit >64 frames inside the loop. Worth fixing as unbounded work (`peers: { where: { serverId: { not: null } } }`); its end state reduces to C4.
- **P5 — Initiator-role livelock between two awake devices** *(25)*. The engine (ICE repair re-taking an evicted socket) is real, but its step 3 assumes D1's ICE handlers survive B's `replace` teardown; they usually will not — a remote PC close surfaces as a `main` close within an RTT and `disconnectFromPeerQuery.ts:119-128` nulls every handler, while `iceConnectionState` degrades only after consent expiry. Expected outcome is C1's initiator arm (D1 goes dark), not a sustained loop. Race-dependent, not established.
- **P6 — Pre-authentication ping makes the client close its own socket** *(28)*. Mechanism confirmed: the server pings from `wsServer.ts:58-62` before any proof, and the SDK answers ahead of the ingress queue (`signalingServerApi.ts:510-531`) → `signalingFrame.ts:38-39` errors because `hasCurrentSocketProof` requires `isVerified` → `:532-538` `socket.close(1011)`. **Primary trigger refuted**: the WASM is awaited *before* the socket is constructed (`signalingServerApi.ts:294-323` vs. `:336`), so no ping can land during a cold fetch. The residual trigger — a >10 s server-side auth stall under Prisma pool exhaustion — is rare.
