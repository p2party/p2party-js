## Implementation Progress & Methodology (protocol-v3)

Protocol-v3 replaces the ad-hoc key exchange of prior versions with a balanced PAKE (CPace over Ristretto255) feeding a Double Ratchet (X25519 DH ratchet + HKDF-SHA512 symmetric ratchet), layered on top of the existing offensive-cryptography transport with its uniform 64 KiB chunk envelope. It is being built test-first and stage by stage: the plan (`docs/superpowers/plans/2026-07-22-pace-ratchet-protocol-v3.md`, committed at `9f8acc3`) decomposes the work into seven stages, each unit gated by a known-answer test (KAT) written and run *failing* before any implementation exists, and each task cleared by a two-stage adversarial review before the next begins. All work lives on `feat/pace-ratchet-protocol-v3`, branched from `master @ 9f8acc3`. This section reports Stage 1 as landed and describes the methodology that governs every stage.

### Stage 1 — cryptographic foundation

Stage 1 delivers the stateless WASM crypto primitives the ratchet is built from. Nine new C exports were added to the libsodium-backed `libcrypto.wasm` module: three CPace/Ristretto255 operations (`cpace_ristretto255_from_hash`, `cpace_ristretto255_scalarmult`, `cpace_ristretto255_scalar_random`), the X25519 DH-ratchet pair (`x25519_keypair`, `x25519_dh`), HKDF-SHA512 built on `crypto_auth_hmacsha512` (`hkdf_sha512_extract`, `hkdf_sha512_expand`), a symmetric ChaCha20-Poly1305 AEAD (`encrypt_chachapoly_symmetric`), and the AEAD message-receive path (`receive_message_with_key`). The work landed across four commits — primitive byte-size constants as the sizing single-source-of-truth (`acd7b69`), the failing KAT suite (`bcaf987`), the C wrappers plus libsodium wiring and rebuilt binary (`351a61c`), and the fixed-heap budget gate (`a848694`) — with two review-driven fix commits (`631335a`, `92b07e8`) interleaved.

The exports are correctness-anchored to authoritative vectors rather than hand-transcribed constants: Ristretto255 `from_hash` and `scalarmult(2·B)` are taken from the vendored libsodium files `test/default/core_ristretto255.exp` and `scalarmult_ristretto255.exp`; the X25519 single-iteration vector from RFC 7748 §5.2; HKDF-SHA512 from RFC 5869-style parameters and additionally recomputed at test time against `node:crypto` `hkdfSync('sha512', …)` as a live oracle; the AEAD vector from RFC 8439 §2.8.2. CPace and X25519 agreement are also computed live in both directions (K₁ = y₁·(y₂·G) = K₂ = y₂·(y₁·G), and DH(a,B) = DH(b,A)), so the suite verifies computed agreement rather than pinned magic. The one unavoidable pinned value — the AEAD KAT — is documented honestly: Bun's `node:crypto` `createCipheriv('chacha20-poly1305', …)` throws `ERR_CRYPTO_UNKNOWN_CIPHER`, so no runtime oracle exists and the RFC 8439 hex is used directly, flagged as a deliberate compromise, not a mock.

The module runs on a **fixed 2 MB heap with growth off**: `INITIAL_MEMORY=2mb` gives 32 × 64 KiB = 2,097,152 bytes, and `ALLOW_MEMORY_GROWTH=0` with `initial === maximum === 32` means the linear memory cannot grow even if the module tried. Commit `a848694` pins this as a runtime budget gate rather than a link-time claim: a fresh module is instantiated on its own 32-page `WebAssembly.Memory`, the largest single Stage-1 operation — `receive_message_with_key` over a full 64 KiB frame — is executed, and the test asserts both that it returns (a negative auth-fail on all-zero input, i.e. it did *not* OOM/abort) and that `buffer.byteLength` is still exactly 2,097,152 afterward, proving zero bytes of growth at runtime and trapping any future change to `maximum` that would silently reintroduce headroom. Adding the Ristretto255/X25519/HKDF/AEAD libsodium sources grew the binary from 136,797 to 158,379 bytes (≈155 KB, a ~22 KB increase under `-O3 -flto --gc-sections`), leaving wide margin under the 2 MB heap; dead-code elimination stripped the unused `core_ed25519` hash-to-curve path so the planned contingency to drop `core_h2c.c` was never needed. The wrappers allocate only stack buffers, and libsodium's `randombytes.c` is deliberately *not* compiled — all entropy is generated in JS and passed in as seeds, with a tiny `getentropy`-backed provider covering the only two exports that need it. A design consequence carried forward: because the WASM heap is fixed but the JS heap can grow, the Double Ratchet's out-of-order skipped-message-key map lives in JS (`state.skipped`, bounded by `MAX_SKIP=512` as an anti-DoS cap), and the WASM exports remain stateless one-shot primitives.

Stage 1 closed green: the KAT suite moved from 0 pass / 8 fail (RED) to 8 pass / 0 fail / 23 `expect()` calls against the rebuilt WASM, the full `pake_ratchet.test.ts` file stands at 9 pass / 0 fail / 25 `expect()` at branch HEAD, and the whole repository regresses clean (`bun test`: 34 pass / 0 fail across 10 files; `npm run typecheck` clean on the production tsconfig). Export existence was proven three independent ways after the production build (`grep` of each symbol in the emitted `libcrypto.js`, a runtime `typeof mod._<name> === 'function'` check for all nine, and the KAT bodies actually reaching each export's assertions), and the SSOT export wiring was verified in all three required locations (`scripts/emscripten.js`, `scripts/libcrypto.d.ts`, and the build-regenerated `src/cryptography/libcrypto.d.ts`).

### Methodology

Every unit follows a strict TDD red-green discipline with the KAT as the gate and 0-fail as the sole pass condition. The failing state is proven *genuine* rather than accidental: for the KAT suite, `beforeAll` loaded the module cleanly from a local `wasmBinary`, so the harness demonstrably reached every test body, and each of the eight failures was a `TypeError: mod._<name> is not a function` naming one specific missing export — cross-checked against the actual pre-Task-3 `libcrypto.js` export list, which contained only the pre-existing `_argon2/_malloc/_free/_sign/_verify/…` symbols and none of the nine new ones. This confirms the RED reason was "not built yet," never a mistranscribed vector or a broken test. Reviewers additionally re-verified the vectors byte-for-byte, diffing the committed test file programmatically against the brief's source fences (the only deltas were a cosmetic formatter line-collapse and a trailing newline) so that every hex constant matched its libsodium/RFC origin verbatim before the suite was accepted.

Each task was gated by a two-stage adversarial subagent review — a spec-compliance pass followed by a code-quality pass — recorded in the progress ledger as "review Approved," with follow-up fixes required to land before the next task proceeded. This produced real, non-cosmetic catches. The code-quality pass caught a `tsc` typing defect where the test passed a `Buffer` (from `readFileSync`) into an emscripten factory typed for `wasmBinary: ArrayBuffer`, fixed by copying into a fresh `ArrayBuffer` (`631335a`) and then promoting that fix into the shared test-module loader so every later task inherits it. It also flagged two exports (`_cpace_ristretto255_scalar_random`, `_hkdf_sha512_expand`) that had been *shadowed* behind earlier `throw`s in their RED bodies, and required Task 3 to independently re-confirm each reaches and passes its own assertions once the earlier calls succeeded.

The headline result of the review, though, was catching a **real design bug in the plan before anything round-tripped**. The plan specified the per-chunk AEAD nonce as `nonce = chunkIndex`. Review recognized this as *physically unrealizable at decrypt time*: `chunkIndex` lives inside the encrypted per-chunk metadata, so the receiver cannot know the nonce until after it has decrypted — yet it needs the nonce *in order to* decrypt. The two obvious repairs are both broken: reusing one message-level value (the 8-byte `N` counter) across every chunk under a single key is catastrophic ChaCha20-Poly1305 nonce reuse, and carrying a raw chunk index in cleartext leaks chunk count and ordering to an on-path observer. The user-approved correction (`92b07e8`) makes the per-chunk nonce a fresh **random 12-byte value carried in the cleartext frame header** — receiver-derivable because it is literally on the wire, metadata-safe because it is random rather than an index, and birthday-safe within a single per-message key — and re-cut the frame layout accordingly (`RATCHET_NONCE_LEN=12`; `CHUNK_HEADER_LEN` 49→61; `MESSAGE_START` 50→62), with the standing rule that a retransmit MUST resend the *identical* cached `(nonce, ciphertext)` pair. Because the receive path was still only smoke-tested when this was found (a garbage frame returns `< 0`) and no send↔receive round-trip yet existed to expose it empirically, the bug would otherwise have survived undetected into a stage where it is far more expensive to unwind — a concrete illustration of the value of adversarial review over self-review. The design doc and global constraints were corrected in the same commit; the C-level frame `#define`s and the placeholder nonce in `receive_message_with_key` are intentionally left at their old values with an in-code note, scheduled for reconciliation in Stage 5 alongside the first real send↔receive round-trip KAT.

### Remaining stages

Stages 2–7 build outward from this foundation — the JS-side ratchet state machine, session and framing integration, the Stage-5 send↔receive round-trip and frame-layout reconciliation, and end-to-end verification — each held to the same KAT-first, review-gated discipline; Stage 2 is already in progress on the branch (`f6debae`). The uniform-chunk transport also pre-provisions a future post-quantum KEM at no wire cost (a reserved `PQ_EPOCH` byte and `PQ_TAG` channel input), since a hybrid ML-KEM/X-Wing ciphertext fits whole inside a single 64 KiB chunk without a v4 wire break.
